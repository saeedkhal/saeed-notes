## compact ولا clear؟

بعد ما خلصنا إصلاحات الأمان، المحادثة بقت طويلة. قدامك اختيارين:

<Grid2>
<Card title="/compact" c={5}>

بيلخّص المحادثة اللي فاتت، ويكمّل في نفس الجلسة بـ context أصغر. ينفع لما تكون لسه شغال على نفس الحاجة ومحتاج مساحة.

</Card>
<Card title="/clear" c={1}>

بيبدأ محادثة جديدة فاضية. ينفع لما تنقل لحاجة مختلفة.

</Card>
</Grid2>

<Hl c="u">compact لما الشغل لسه هو هو. clear لما الشغل يتغير</Hl>.

صاحب الكورس بيقول إنه مش بيستخدم compact كتير. لأن غالبًا لما الـ context يتملي، بيبقى خلص الـ feature أصلًا، فيعمل clear ويبدأ من جديد. وقبل ما تختار، `/context` بيوريك إيه اللي مالي الـ context.

## plan mode مش دايمًا أول خطوة

plan mode بينفع لما تكون عارف إنت عايز إيه، ومحتاج Claude يعرف هينفذه إزاي جوه الكود. مثلًا "products و categories و stock بـ Postgres و Drizzle" طلب واضح.

لكن "اعمل inventory management كويس" طلب مش واضح. يعني إيه بالظبط؟ كذا مخزن؟ حجز للمنتجات؟ تنبيه لما المخزون يقل؟ تاريخ لكل حركة؟ لو دخلت بالطلب ده plan mode على طول، Claude هو اللي هيقرر كل ده بدالك.

الحل إنك تفصل المراحل:

<Flow items={[{t: "Scope", s: "هنبني إيه؟", c: 5}, "→", {t: "Architect", s: "القرارات التقنية", c: 3}, "→", {t: "Plan mode", s: "ننفذ إزاي؟", c: 1}]} />

صاحب الكورس عنده workflow مفتوح المصدر مبني على skills بالشكل ده:

- **scope**: بيحوّل الفكرة لـ scope واضح، ويناقشها قبل أي كود، ويفضل يحدّثها مع الشغل.
- **architect**: بيمشي معاك في القرارات التقنية المهمة.
- **plan mode**: بيحدد التغيير ده هيدخل في الكود الحالي إزاي.

وفي نفس الـ workflow فيه skills تانية: audit بتدرس الموجود، و develop بتنفذ، و check بتراجع، و test للتستات، و document للتوثيق، و sync بتحدّث ملفات الـ context من آخر commits، و debug بتعمل debugging بخطوات منظمة بدل ما تغيّر ملفات عشوائي لحد ما حاجة تشتغل.

مش كل feature محتاجة كل ده. الفصل ده بيفرق لما التطبيق يكبر.

<Box type="tip" title="متستخدمش كل حاجة عشان إنت عارفها">

تغيير عنوان؟ اطلبه على طول. schema؟ plan mode. فكرة لسه مش واضحة؟ حدد الـ scope الأول. كل خطوة زيادة من غير سبب بتضيّع وقت.

</Box>
