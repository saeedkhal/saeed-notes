## SQL ممتازة لما بتدور على حاجة معروفة

رقم أوردر، إيميل، SKU، رقم فاتورة. دي قيم معروفة، ولو عملت index صح على العمود، Postgres و SQL Server بيرجعوا الصف بسرعة. مش بتقارن "أنهي نتيجة أحسن". يا الصف ده يا لأ.

## `LIKE` بيبدأ كويس وبعدين الأسئلة بتخلص

في أول نسخة من المتجر ممكن تكتب:

```sql
SELECT id, name
FROM products
WHERE name ILIKE '%iphone%' OR description ILIKE '%iphone%';
```

على كام ألف منتج ممكن تعدّي. `%` في أول الكلمة غالبًا بتلغي فايدة الـ B-tree index، فالداتابيز بتمسح صفوف كتير. ولسه متجاوبتش على الأسئلة اللي اليوزر حاسس بيها:

- ظهور الكلمة في `name` أهم من ظهورها في `description`؟
- الكفر "compatible with iPhone 15 Pro" ليه طالع فوق الموبايل نفسه؟
- `ifone` يرجّع ولا يقول مفيش نتائج؟
- عدد المنتجات لكل brand، والاقتراحات وأنت بتكتب، ومقطع الـ description اللي فيه الماتش؟

Postgres عنده full-text search (`tsvector`) وده أحسن من `LIKE` بكتير للبحث بالنص. الأداة مش هي الحكم. الحكم: هل محتاج ranking و typos و facets و autocomplete على تجربة بحث أساسية، ولا لأ.

<Box type="tip" title="متحوّلش كل بحث لـ Elasticsearch">

صفحة الأدمن اللي بتدور فيها على SKU أو إيميل عميل تفضل كويري SQL. محرك البحث مش بديل للداتابيز، هو خدمة زيادة لتجربة البحث.

</Box>

## باب البحث غير باب البيزنس

حتى لو ركّبت Elasticsearch، الـ SQL مش بتمشي. الأوردر والفلوس والعلاقات والـ constraints محتاجين transactions. الداتابيز بتفضل <En>source of truth</En>. Elasticsearch بيبقى <En>search index</En>: نسخة متشكّلة عشان البحث، مش عشان تتحاسب منها.

اليوزر مش بيعرف الفرق. الـ API هو اللي بيفرق: صفحة النتائج تسأل Elasticsearch، والـ checkout يسأل SQL. المخزون اللي اتخصم لحظة الدفع بيتقرأ من SQL، حتى لو سيرش من ثواني كان لسه كاتب "متوفر".
