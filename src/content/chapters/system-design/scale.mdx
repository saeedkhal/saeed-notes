## البداية: سيرفر واحد شايل كل حاجة

في الأول، الـ web app والداتابيز والكاش كلهم قاعدين على ماكينة واحدة. زي محل كشري صغير: نفس الراجل بياخد الأوردر ويطبخ ويحاسب.

1. اليوزر بيكتب الدومين، والـ <En>DNS</En> (غالبًا خدمة خارجية) بيترجمه لـ IP — زي دليل التليفونات.
2. البراوزر أو الموبايل بياخد الـ IP ويبعت HTTP request للسيرفر على طول.
3. السيرفر بيرد بـ HTML لو ويب، أو JSON لو API للموبايل.

<Box type="tip" title="مصدرين للترافيك">

الويب: لوجيك على السيرفر + HTML/JS للعرض. الموبايل: بيكلم السيرفر بـ HTTP والرد غالبًا JSON لأنه خفيف وسهل.

</Box>

## أول فصل: الداتابيز في سيرفر لوحدها

أول ما اليوزرز يزيدوا، بنفصل سيرفر الويب عن سيرفر الداتا. المزية إن كل واحد فيهم يكبر لوحده.

| النوع | أمثلة | إمتى تختاره؟ |
| --- | --- | --- |
| Relational (SQL) | PostgreSQL, MySQL, Oracle | الاختيار الافتراضي: جداول وعلاقات و `JOIN`، ومستقر من عشرات السنين |
| Non-Relational (NoSQL) | Cassandra, DynamoDB, MongoDB, Neo4j | latency قليلة جدًا، أو الداتا مش متهيكلة، أو كمية مهولة، أو بس بتعمل serialize لـ JSON |

## الـ Load Balancer: عسكري المرور

بيقف قدام السيرفرات ويوزّع الترافيك عليهم. اليوزر بيكلم IP عام واحد بتاع الـ LB، والسيرفرات نفسها بتتكلم على <En>private IPs</En> مش ظاهرة للإنترنت.

<Flow label="Load balancer" items={[

  "→",

  "⇉",
  { t: "Server 1", c: 3 },
  { t: "Server 2", c: 4 },

سيرفر وقع؟ الـ LB يحوّل الترافيك على الباقيين وخلاص. الترافيك زاد؟ ضيف سيرفرات للـ pool والـ LB يبتدي يبعتلهم تلقائي.

<Box type="interview" title="في الإنترفيو">

كده الـ web tier بقى تمام. بس الداتابيز لسه نسخة واحدة — يعني لو وقعت كله وقع.

</Box>

## نسخ الداتابيز

نسخة رئيسية (<En>Primary</En>) بتستقبل الكتابة بس، ونسخ (<En>Replicas</En>) بتاخد نسخة من الداتا وبتخدم القراءة. أغلب التطبيقات القراءة فيها أكتر بكتير من الكتابة، فعدد الـ replicas بيبقى أكبر.

| المكسب | ليه؟ |
| --- | --- |
| Performance | القراءات بتتوزع على كذا نسخة بالتوازي |
| Reliability | لو سيرفر اتدمر، الداتا موجودة في أماكن تانية |
| Availability | نسخة وقعت؟ الشغل يكمل من نسخة تانية |

<Box type="warn" title="طب لو حاجة وقعت؟">

**Replica وقعت:** القراءة تتحول مؤقتًا لنسخة تانية (أو للـ primary لو مفيش غيرها) لحد ما تقوم واحدة جديدة.

**Primary وقع:** نرقّي replica تبقى primary. خد بالك: الـ replica ممكن تكون متأخرة شوية، فبنكمّل الناقص بـ recovery. في الحقيقة الموضوع أعقد، وفيه حلول زي multi-master.

</Box>

## الكاش: الدرج اللي جنبك

بدل ما كل مرة تنزل المخزن (الداتابيز) تجيب نفس الحاجة، تحطها في درج جنبك في الميموري. الكاش تخزين مؤقت وسريع للحاجات التقيلة أو اللي بتتطلب كتير.

<Flow label="Cache-aside" items={[
  { t: "Web Server", c: 1 },
  "→",
  { t: "Cache", s: "موجود؟ رجّعه", c: 3 },
  "→",
  { t: "DB", s: "مفيش؟ هات وخزّن", c: 5 },
]} />

أدوات شائعة: Memcached و Redis، بـ API بسيط زي `set(key, value, ttl)` و `get(key)`.

| النقطة | المعنى بالمصري |
| --- | --- |
| إمتى أستخدمه | الداتا بتتقرى كتير وبتتغير قليل. ومتخزنش فيه حاجة مهمة لوحدها — الميموري بتتمسح لو السيرفر عمل restart |
| Expiration | لازم مدة صلاحية. قصيرة قوي = هترجع للداتابيز كتير. طويلة قوي = داتا بايتة |
| Consistency | الكتابة في الداتابيز والكاش مش في transaction واحدة، فممكن يحصل اختلاف |
| SPOF | كاش سيرفر واحد = نقطة فشل واحدة. خلّي عندك أكتر من سيرفر |
| Eviction | الكاش اتملى؟ ترمي حاجة. الأشهر LRU (الأقدم استخدامًا)، وفيه LFU و FIFO |

<Box type="tip" title="امتى الكاش فكرة وحشة؟">

لما الداتا بتتغير كتير، أو لو هتعتمد عليه كمخزن دائم. الكاش درج، مش خزنة.

</Box>

## الـ CDN: فروع قريبة من اليوزر

شبكة سيرفرات منتشرة في العالم بتشيل المحتوى الثابت: صور، فيديو، CSS، JS. اليوزر اللي في القاهرة ياخد الصورة من أقرب سيرفر ليه بدل ما تيجي من أمريكا.

<Flow label="CDN" items={[
  { t: "User", c: 1 },
  "→",
  { t: "CDN", s: "فيها الصورة؟", c: 2 },
  "→",
  { t: "Origin", s: "S3 أو السيرفر + TTL", c: 4 },
]} />

<Box type="warn" title="خد بالك من الفلوس">

- **التكلفة:** بتدفع على الداتا اللي بتطلع — متحطش فيها حاجات نادرًا ما حد بيطلبها.
- **مدة الكاش:** مش طويلة لدرجة إن المحتوى يبوظ، ولا قصيرة لدرجة إنها ترجع للـ origin كل شوية.
- **لو الـ CDN وقعت:** التطبيق لازم يعرف يجيب الملفات من الـ origin مباشرة.
- **Invalidation:** تمسح ملف قبل ما يخلص بـ API من المزوّد، أو تستخدم versioning زي `?v=2`.

</Box>

## سيرفر من غير ذاكرة

عشان نكبّر الـ web tier بالعرض بحرية، لازم نشيل الـ state (زي الـ session بتاعة اليوزر) من جوه السيرفر.

<Grid2>
<Card title="😖 Stateful" c={2}>

بيانات اليوزر A محفوظة في Server 1 بس. يبقى لازم كل ريكوست بتاعه يروح لـ Server 1 (sticky sessions). إضافة أو شيل سيرفر بقت وجع دماغ، والـ failover صعب.

</Card>
<Card title="😎 Stateless" c={3}>

الـ session متخزنة في مكان مشترك (Redis أو NoSQL أو RDBMS). أي سيرفر يقدر يخدم أي ريكوست. تقدر تعمل auto-scaling براحتك.

</Card>
</Grid2>

<Box type="story" title="تشبيه الجرسون">

مطعم الجرسون فيه حافظ أوردرك في دماغه = Stateful. مطعم الأوردر مكتوب في سيستم أي جرسون يشوفه = Stateless. في التاني، لو الجرسون راح، حد تاني يكمل عادي.

</Box>

## أكتر من Data Center

لما يبقى عندك يوزرز في كذا قارة، بتوزع السيستم على كذا داتا سنتر. الـ <En>GeoDNS</En> بيوجّه كل يوزر لأقرب داتا سنتر ليه. ولو داتا سنتر وقع كله، الترافيك يروح على اللي شغال.

<Box type="idea" title="التحديات">

- **توجيه الترافيك:** الـ DNS لازم يكون ذكي ويعرف الأقرب.
- **مزامنة الداتا:** لو يوزر اتحول لداتا سنتر تاني، لازم يلاقي داتاه هناك — replication بين الداتا سنترز.
- **التيست والـ deployment:** تجرب من أماكن مختلفة، وأدوات تخلي كل الداتا سنترز على نفس النسخة.

</Box>

## صندوق البوستة: Message Queue

كومبوننت بيخزن رسايل وبيسمح بشغل asynchronous. الـ Producer بيرمي رسالة في الطابور، والـ Consumer بيسحبها ويشتغل عليها لما يفضى.

<Flow label="Message queue" items={[
  { t: "Web Server", s: "Producer", c: 1 },
  "→",
  { t: "Queue", c: 4 },
  "→",
  { t: "Workers", s: "Consumers", c: 3 },
]} />

المزية الكبيرة <En>decoupling</En>: الـ producer يقدر يبعت حتى لو الـ consumer مش متاح. ولو الطابور كبر، زوّد workers. لو فاضي، قلّلهم.

<Box type="story" icon="🖼️" title="مثال عملي">

يوزر رفع صورة وعايز فلتر وقص وضغط — ده بياخد وقت. بدل ما يستنى، السيرفر يرمي المهمة في الطابور ويرد عليه فورًا، والـ workers يخلصوها في الخلفية.

</Box>

## اللوجز والمقاييس والأوتوميشن

لما السيستم يكبر، لازم تشوف جواه وتشغّله من غير ما تعمل كل حاجة بإيدك.

| الأداة | الفايدة |
| --- | --- |
| Logging | تتابع الإيرورز. الأحسن تجمعها في مكان مركزي بدل ما تدخل على كل سيرفر |
| Metrics | Host: CPU وميموري و Disk I/O. Aggregated: أداء الداتابيز كطبقة. Business: DAU و retention و revenue |
| Automation | CI بيتأكد إن كل commit سليم، وأوتوميشن للـ build والتيست والـ deploy |

## تكبير الداتابيز: Sharding

نفس فكرة الـ web tier. Vertical (ماكينة أقوى) ليه سقف وتكلفته عالية وبيبقى SPOF. Horizontal = <En>sharding</En>: تقسم الداتا على كذا داتابيز.

كل shard ليه نفس الـ schema بس فيه جزء مختلف من الداتا. بتختار <En>sharding key</En> (زي `user_id`) ودالة زي `user_id % 4` تحدد اليوزر ده في أنهي shard. أهم قاعدة: اختار key يوزّع الداتا بالتساوي.

<Flow label="Sharding" items={[

  "→",
  { t: "Shard 0", c: 2 },
  { t: "Shard 1", c: 3 },
  { t: "Shard 2", c: 4 },
  { t: "Shard 3", c: 5 },
]} />

| المشكلة | الشرح والحل |
| --- | --- |
| Resharding | shard اتملى أو التوزيع مش متساوي، فلازم تغيّر الدالة وتنقل داتا. الحل الشهير: Consistent Hashing (الفصل الجاي) |
| Celebrity / Hotspot | shard عليه يوزرز مشاهير فبيتضرب ضرب. الحل: تدي كل مشهور shard لوحده، أو تقسم أكتر |
| Join | الـ JOIN بين shards صعب. الحل الشائع: de-normalize وتكرر الداتا عشان الكويري يتعمل على جدول واحد |

ممكن كمان تنقل حاجات من الداتابيز لـ NoSQL عشان تخفف الحمل، خصوصًا الداتا اللي مش محتاجة علاقات.
