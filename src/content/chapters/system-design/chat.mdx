## السيرفر يوصل للـ client إزاي؟

الـ HTTP عادةً الـ client هو اللي بيبدأ. طب إزاي السيرفر يبعت رسالة جت لسه؟

| الطريقة | الفكرة | الحكم |
| --- | --- | --- |
| Polling | الـ client يسأل كل شوية "فيه جديد؟" | هدر، وأغلب الردود فاضية |
| Long Polling | يفضل الكونكشن مفتوح لحد ما يجي جديد أو timeout | أحسن، بس صعب مع load balancer ومش دايمًا يعرف إن اليوزر خرج |
| WebSocket | كونكشن مستمر في الاتجاهين | ده الاختيار للإرسال والاستقبال |

<Hl c="p">الـ WebSocket هو اللي بنبني عليه الشات</Hl>. تسجيل الدخول والبروفايل والجروبات يفضلوا HTTP عادي ورا load balancer.

## المعمارية

<Grid2>
<Card title="Stateless" c={3}>

تسجيل دخول، بروفايل، جروبات — HTTP عادي ورا load balancer. أي سيرفر يخدم أي ريكوست.

</Card>
<Card title="Stateful" c={2}>

سيرفرات الشات: كل client ماسك WebSocket مع سيرفر معيّن. Service discovery (زي Zookeeper) بيختارلك أنسب سيرفر.

</Card>
</Grid2>

تخزين الرسايل: حجم ضخم، والوصول غالبًا للرسايل الجديدة. Key-value store زي HBase أو Cassandra مناسب.

الـ message ID لازم يكون فريد ومرتب بالوقت (Snowflake، أو sequence محلي لكل محادثة).

ولو اليوزر offline: push notification.

لو B أونلاين: Chat Server 2 يوصّله الرسالة على الـ WebSocket. لو أوفلاين: Push Notification.

- **كذا جهاز:** كل جهاز فاكر `cur_max_message_id` وبيجيب أي رسالة أحدث منه.
- **جروب صغير:** الرسالة تتنسخ في "صندوق" كل عضو — بسيط لحد عدد أعضاء معيّن.
- **Online presence:** Heartbeat كل كام ثانية. لو انقطع فترة يبقى offline، عشان النت الضعيف مايخليش الحالة تتقلب كل ثانية. التحديث بيوصل للصحاب عن طريق pub/sub.

<Box type="story" title="تشبيه">
