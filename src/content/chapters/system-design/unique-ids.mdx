## ليه `auto_increment` مش كفاية؟

الـ `auto_increment` بتاع الداتابيز مابيشتغلش كويس لما يبقى عندك كذا سيرفر. المطلوب IDs: <Hl c="g">فريدة، أرقام بس، ٦٤ بت، مرتبة بالوقت، وآلاف في الثانية</Hl>.

## أربع طرق

| الطريقة | الفكرة | الحكم |
| --- | --- | --- |
| Multi-master | كل سيرفر يزود بـ k (عدد السيرفرات) | صعب تكبّره، ومش مرتب بالوقت عبر السيرفرات |
| UUID | ١٢٨ بت عشوائي، كل سيرفر يولّد لوحده | سهل ومفيش تنسيق. طويل، مش رقم، ومش مرتب |
| Ticket Server | سيرفر مركزي واحد بيوزع أرقام | بسيط. بس SPOF: لو وقع، محدش يقدر يولّد ID |
| Snowflake | تقسم الـ ٦٤ بت لأجزاء | ده الحل اللي بنرشّحه |

## تشريح الـ Snowflake ID

| الجزء | الحجم | بيعمل إيه |
| --- | --- | --- |
| sign | ١ بت | دايمًا ٠، عشان الرقم يفضل موجب |
| timestamp | ٤١ بت | ملي ثانية من epoch مخصص — يكفي حوالي ٦٩ سنة، وبيخلي الـ IDs مرتبة بالوقت |
| datacenter | ٥ بت | ٣٢ داتا سنتر |
| machine | ٥ بت | ٣٢ ماكينة في كل داتا سنتر |
| sequence | ١٢ بت | ٤٠٩٦ ID لكل ماكينة في كل ملي ثانية |

<Box type="story" title="تشبيه">

تخيّل رقم الفاتورة في سلسلة مطاعم: التاريخ والساعة في الأول (عشان الترتيب)، بعدين رقم الفرع، بعدين رقم الكاشير، بعدين عدّاد الفواتير في نفس الثانية. مفيش فرعين هيطلعوا نفس الرقم، ومش محتاجين يتصلوا ببعض كل فاتورة.

</Box>

<Box type="warn" title="خد بالك">

**Clock sync:** ساعات السيرفرات لازم تكون متزامنة (NTP). لو ساعة رجعت لورا، ممكن تطلع IDs مكررة.

تقدر تعدّل أطوال الأجزاء حسب احتياجك (داتا سنترز أكتر؟ قصّر الـ sequence). وفكّر في high availability: مولّد الـ ID نفسه مايبقاش نقطة فشل واحدة.

</Box>
