## Incident وقت campaign

منصة e-commerce بدأت حملة الساعة `20:00`. الترافيك قفز من `800` إلى `6,000 request/min`، والـ p95 latency وصل `1.8s`. عندها ALB قدام Auto Scaling Group موزعة على AZs.

## Timeline من الضغط للاستقرار

1. **20:00:** `desired=2` وCPU المتوسطة `35%`.
2. **20:04:** CPU تعدي `70%` حسب policy لمدة التقييم.
3. **20:06:** Auto Scaling تعمل scale out من `2` إلى `4 instances`.
4. **20:08:** instances الجديدة تكمل bootstrap وتنجح في health checks.
5. **20:09:** ALB يبدأ يوجه لها requests؛ الـ p95 يرجع `320 ms`.
6. **22:30:** الحمل يهدى، وبعد stabilization تعمل المجموعة scale in من غير النزول تحت `min=2`.

النجاح إن latency رجعت للهدف، والـ instances غير السليمة ما استقبلتش traffic، والسعة رجعت بعد الذروة. الفشل إن policy تضيف instances أسرع من جاهزيتها، أو إن bottleneck الحقيقي database.

<Box type="story" icon="📈" title="دوران مختلفان">

ELB يقرر أي target سليمة تستقبل الطلب الحالي. EC2 Auto Scaling يقرر عدد instances ويحافظ عليه. واحد يوزع traffic والتاني يدير fleet.

</Box>

## Elastic Load Balancing

`ELB` اسم العيلة. الـ load balancer يستقبل الترافيك ويوجهه لـ targets سليمة في target groups، ويعمل health checks بدل ما يبعت الطلب لسيرفر تعبان.

## EC2 Auto Scaling

الـ <En>Auto Scaling Group</En> ليها:

- `minimum`: أقل عدد تحافظ عليه.
- `desired`: العدد المطلوب حاليًا.
- `maximum`: السقف اللي متعديهوش.
- launch template يصف instance الجديدة.
- scaling policies مبنية على metric أو schedule أو توقع.

لو instance بقت unhealthy، المجموعة تقدر تستبدلها. ولما تربط target group، الـ instances الجديدة تتسجل والقديمة تتشال تلقائيًا.

<Hl c="b">ELB يوزّع الطلبات؛ Auto Scaling يغيّر عدد الـ instances. الاتنين بيكملوا بعض، مش نفس الخدمة.</Hl>

وقت الحملة، policy تعمل scale out. بعد الزحمة، تعمل scale in ضمن الحدود. التطبيق لازم يبقى مستعد: session مش متعلقة بقرص instance واحدة، والـ instances قابلة للاستبدال.

## قارن القرارات

- **Vertical scaling:** موارد أكتر لنفس instance؛ له سقف وقد يحتاج downtime.
- **Horizontal scaling:** instances أكتر؛ يحتاج تطبيقًا قابلًا للتوزيع والاستبدال.
- **ALB:** HTTP/HTTPS وLayer 7 وhost/path routing.
- **NLB:** TCP/UDP وLayer 4 وخصائص أداء وشبكة.
- **GWLB:** fleet من virtual network appliances.
- **Health check:** تمنع توجيه الطلب لـ target غير سليمة؛ مش اختبارًا كاملًا لكل business function.

## 🧪 تمرين ورقة: احسب الاستجابة

ابدأ بـ `min=2`, `desired=2`, `max=8`. الحمل يتضاعف كل دقيقتين، والـ instance تحتاج ٤ دقائق لتصبح healthy. اكتب timeline من أول alarm لحد رجوع latency، وحدد metric وthreshold وstabilization. بعدين افترض إن database هي bottleneck واشرح ليه web scale out قد يفشل.

<Box type="warn" title="Scaling مش علاج لكل مشكلة">

لو query قاعدة البيانات بطيئة، إضافة web servers ممكن تزود الضغط عليها. راقب bottleneck، وحط cooldown أو stabilization مناسب، ومتخليش policy تتأرجح.

</Box>

## اختار من كلمات السؤال

`HTTP path routing` → ALB. `TCP/UDP أو Layer 4` → NLB. `fleet of security appliances` → GWLB. `يحافظ على العدد ويستبدل unhealthy` → EC2 Auto Scaling.

الفصل الجاي هنسيب إدارة السيرفرات ونشغّل أجزاء من الـ workload كـ events على Lambda.
