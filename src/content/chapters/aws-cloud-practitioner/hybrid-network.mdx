## المثال الأول: ERP بين data center وAWS

شركة تنقل ERP تدريجيًا. عندها `12` VPC وdata center يرسل `3 TB/day`. المطلوب encryption، latency مستقرة، وbackup path يشتغل خلال `10 دقايق`.

١. `Direct Connect` يوفر اتصال مخصص أكثر ثباتًا من internet path.
٢. لأنه مش encrypted تلقائيًا لمجرد إنه خاص، يتصمم encryption مناسب حسب المتطلب.
٣. `Site-to-Site VPN` يبقى backup عبر الإنترنت.
٤. `Transit Gateway` يربط الـ VPCs والاتصالات كـ hub مع route tables للعزل.
٥. failover test يقيس التحويل والـ routes والـ throughput، مش مجرد إن tunnel حالتها UP.

`Direct Connect` يحتاج lead time وتكلفة ومزود/موقع مناسب، لكنه يقدم مسار مخصص. Site-to-Site VPN مفيد كبداية أو backup، لكن قارن bandwidth والـ SLA الفعليين.

## PrivateLink وTransit Gateway

`PrivateLink` يعرّض service محددة من provider VPC لمستهلكين عبر interface endpoints، من غير full network connectivity، ويفيد مع overlapping CIDRs. مناسب لشركة شريكة تحتاج payments API فقط.

`Transit Gateway` راوتر hub يربط VPCs وon-premises. هو full routing fabric حسب route tables، مش بديل PrivateLink لعرض API واحدة بأقل blast radius.

## Incident timeline

- `02:00`: Direct Connect path يقع.
- `02:01`: BGP/route behavior يبدأ التحويل حسب التصميم.
- `02:06`: VPN شغالة، لكن throughput أقل من replication traffic.
- `02:15`: queue backlog يزيد؛ الـ RTO network اتحقق، لكن capacity objective فشل.

النجاح محتاج test تحت traffic حقيقي: زمن التحويل، packet loss، throughput، وعودة المسار الأساسي من غير route oscillation.

<Box type="warn" title="Overlapping CIDR يقفل اختيارات">

Full routing بين شبكتين بنفس العناوين صعب. خطط IPAM بدري؛ ولو المطلوب service واحدة فقط، PrivateLink قد يتجنب full-network overlap.

</Box>
