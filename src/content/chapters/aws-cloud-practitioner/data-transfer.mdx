## نقل data platform من غير downtime طويل

المؤسسة عندها Oracle 12 TB، NAS حجمه 300 TB، partner يبعت SFTP يوميًا، وbackup application محتاج tape interface.

1. `DMS Schema Conversion` يقيّم Oracle schema ويحول المدعوم لـ Aurora PostgreSQL.
2. الفريق يصلح procedures غير المدعومة ويعمل tests.
3. `DMS` يعمل full load ثم CDC؛ lag ينزل من 40 دقيقة لأقل من دقيقتين.
4. `DataSync` ينقل NAS إلى S3 على waves ويتحقق من النقل.
5. `Transfer Family` يوفر SFTP endpoint للـ partner من غير تغيير برنامجه.
6. `Tape Gateway` يحافظ على virtual tape workflow.

## Database: data غير schema

`DMS` ينقل ويكرر rows بين مصادر وtargets مدعومة، one-time أو CDC. `DMS Schema Conversion` يحول schema والكود المدعوم؛ و`SCT` اسم أقدم قد يظهر في CLF-C02.

Cutover الساعة 02:00 ينجح لو CDC lag صفر، row counts/checksums مقبولة، والتطبيق يكتب على target. لو rows اتنقلت لكن stored procedure حرجة فشلت، migration فشلت وظيفيًا.

## Files والبروتوكول والـ hybrid

- `DataSync`: bulk أو scheduled online transfer لـ file/object data بين on-prem وAWS أو خدمات مدعومة.
- `Transfer Family`: endpoints مُدارة لـ SFTP/FTPS/FTP إلى S3 أو EFS.
- `Storage Gateway`: integration مستمر؛ S3 File Gateway، FSx File Gateway، Volume Gateway، Tape Gateway.

DataSync مشروع copy/sync؛ Storage Gateway interface مستمرة مع cache محلي؛ Transfer Family يحافظ على بروتوكول شريك.

## لما الشبكة متكفيش

300 TB على وصلة فعلية 1 Gbps تحتاج نظريًا حوالي 28 يوم نقل متواصل قبل overhead، فممكن physical transfer يبقى أنسب.

في **أكتوبر ٢٠٢٦**، Snow Family غير متاح لعملاء commercial جدد، ودعم Snowball في commercial Regions مقرر ينتهي **٣١ ديسمبر ٢٠٢٦**. الاتجاه الحالي `AWS Data Transfer Terminal` وحلول partners حسب البلد والسعة. الامتحان المنشور قد يسأل Snow Family تاريخيًا، فاعرف الغرض والـ caveat.
