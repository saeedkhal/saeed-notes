## Incident: instance اتبدلت والتطبيق مرجعش

تطبيق SaaS كان شغال على EC2 واحدة. بعد `Stop/Start` تغير الـ public IPv4، والـ user data القديمة كانت تعتمد على secret مكتوب داخلها، والـ root volume كان إعداد حذفه عند termination غير مفهوم للفريق.

المشكلة كشفت إن الـ instance لازم تتوصف كمجموعة قرارات قابلة للإعادة، مش جهاز يتظبط يدويًا مرة.

## Launch flow من الصفر

1. اختار `AMI` تحدد نظام التشغيل ومعلومات الإقلاع.
2. اختار `instance type` حسب CPU وmemory وnetwork الفعلية.
3. حدد VPC/subnet وSecurity Group تسمح فقط بالترافيك المطلوب.
4. اربط IAM role بدل access keys ثابتة.
5. اربط EBS وحدد `DeleteOnTermination` بوعي.
6. شغّل bootstrap قابل للإعادة، ثم health check وmonitoring.

النجاح إن instance بديلة توصل لنفس الحالة من automation وتدخل الخدمة خلال الهدف. الفشل إن recovery يعتمد على تعديل يدوي أو secret داخل user data.

<Box type="story" icon="🧩" title="أربع قرارات مختلفة">

الـ AMI تحدد البداية البرمجية، والـ instance type يحدد الموارد، والـ Security Group يضبط الترافيك، والـ purchase option يغير نموذج السعر. واحد منهم مش بديل للتاني.

</Box>

## AMI + instance type

الـ <En>Amazon Machine Image</En> قالب فيه نظام التشغيل ومعلومات الإقلاع، وممكن يكون AWS-provided أو من Marketplace أو معمول عندك. الـ AMI مرتبطة بـ Region، وتقدر تنسخها حسب احتياجك.

عائلات الـ instances بتلمّح لطبيعة الموارد:

- `T` و`M`: استخدام عام؛ بداية منطقية لتطبيقات متنوعة بعد القياس.
- `C`: compute optimized للحسابات الكثيفة.
- `R` و`X`: memory optimized للأحمال اللي محتاجة RAM كبيرة.
- `I` و`D`: storage optimized لأحمال I/O أو تخزين محلي مخصوص.
- عائلات accelerated computing للـ GPU والـ ML والجرافيكس.

<Hl c="g">اختار على قياس الـ workload والـ metrics، مش على أكبر رقم.</Hl>

## User data والـ bootstrap

`User data` تعليمات تتنفذ غالبًا وقت أول إقلاع عشان تثبّت web server أو تنزّل التطبيق. دي مش مكان مناسب لـ passwords أو access keys مكتوبة صراحة.

<Box type="tip" title="خلّي البداية قابلة للإعادة">

لو السيرفر وقع وAuto Scaling عمل واحد جديد، تعليمات الإعداد لازم توصّله لنفس الحالة. خزّن الأسرار في خدمة مخصصة، وادّي الـ instance IAM role بدل credentials ثابتة.

</Box>

## Security Group

الـ Security Group firewall افتراضي مرتبط بالـ network interface. قواعده **stateful**: لو سمحت بطلب داخل، الرد مسموح من غير قاعدة عكسية منفصلة.

لـ web tier، افتح `HTTPS` من الجمهور، وخلّي الإدارة عبر مسار موثوق عند الضرورة. متفتحش كل البورتات لكل الإنترنت لمجرد إن التجربة «تشتغل».

`Reboot` يعيد تشغيل نفس الـ instance. `Stop/Start` يوقف compute ثم يبدأها، وقد تتغير public IPv4 غير الثابتة. `Terminate` إنهاء، وممكن الـ root EBS يتحذف حسب إعداد `DeleteOnTermination`.

حتى لو instance واقفة، موارد زي EBS volume أو Elastic IP غير مستخدم ممكن تفضل بتتحاسب.

`Spot` يستغل سعة فائضة بخصم، لكن AWS ممكن تقاطعها بإشعار قصير؛ مناسب لشغل قابل للإعادة، مش نسخة production وحيدة لا تتحمل الانقطاع. `Dedicated Hosts/Instances` للعزل أو متطلبات ترخيص مخصوصة، وتكلفتها أعلى عادةً.

## Timeline لدورة الحياة

- **pending → running:** الـ instance تتجهز ثم يبدأ compute billing حسب نموذج التسعير.
- **reboot:** نفس الـ instance تعيد التشغيل.
- **stop/start:** compute يتوقف ثم يبدأ، وقد تتغير public IPv4 غير الثابتة.
- **terminate:** instance تنتهي؛ مصير root EBS يعتمد على الإعداد.

Stop مش cleanup كامل: EBS وElastic IP وموارد أخرى ممكن تفضل بتتحاسب.

## 🧪 Lab ورقي آمن

صمم instance لـ API: `AMI: Linux`، family مبدئية، inbound `443` من ALB فقط، role لقراءة object محدد، وuser data بلا secrets. اكتب timeline لاستبدالها بعد failure خلال ١٠ دقائق، وحدد دليل نجاح الـ bootstrap.

مفيش resource هيتعمل. لو طبّقت فعليًا، راجع السعر أولًا، اقفل المنافذ الزيادة، وبعد التجربة اعمل terminate واحذف volumes أو IPs غير المطلوبة.

## متخلطش بينهم
