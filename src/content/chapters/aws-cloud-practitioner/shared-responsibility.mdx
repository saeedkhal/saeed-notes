## Incident: vulnerability على EC2

شركة fintech شغالة على EC2. الساعة `03:00` scanner اكتشف vulnerability حرجة في guest OS. الفريق قال في البداية «السيرفر عند AWS»، لكن ده خلط بين البنية المادية والطبقة اللي العميل اختار يديرها.

## Timeline: مين يتحرك؟

1. AWS تدير data center والهاردوير والشبكة الأساسية والـ hypervisor.
2. العميل يحدد الـ AMI ويشغل guest OS، وبالتالي يخطط patching له.
3. **03:10:** فريق الأمن يحدد instances المتأثرة من inventory.
4. **03:25:** يبني image محدثة ويختبر التطبيق عليها.
5. **04:00:** يستبدل instances تدريجيًا ويراقب errors.
6. **04:30:** evidence يثبت version الجديدة، ثم تتراجع السياسات لمنع تكرار التأخير.

النجاح إن كل مهمة لها owner قبل incident. الفشل إن patch يتأخر لأن كل طرف افترض إن الطرف الآخر مسؤول.

## الخط الفاصل بيتحرك حسب الخدمة

AWS Shared Responsibility Model بيقسم الأمان:

- **Security of the cloud:** AWS تحمي البنية اللي تشغّل خدمات AWS: المرافق، الهاردوير، الشبكات الأساسية، وطبقة الافتراضية.
- **Security in the cloud:** العميل يحمي اللي يضعه ويضبطه: الداتا، الهويات، الإعدادات، والصلاحيات، ومسؤوليات إضافية حسب الخدمة.

<Hl c="p">AWS تؤمّن الـ Cloud، والعميل يؤمّن استخدامه للـ Cloud.</Hl>

## مثال EC2

مع Amazon EC2، AWS تدير data center والهاردوير والـ hypervisor. العميل يدير guest OS وتحديثاته، التطبيق، security groups، IAM، والتصنيف والتشفير المناسب للداتا.

لو نظام التشغيل قديم واتخترق، مينفعش نقول إن السيرفر المادي عند AWS وخلاص. الطبقة اللي اخترنا نديرها مسؤوليتنا.

## مثال خدمة مُدارة

مع خدمة database مُدارة، AWS قد تدير نظام التشغيل وطبقة قاعدة البيانات أو أجزاء أكبر من الصيانة. العميل يفضل مسؤولًا عن اختيار الإعدادات، المستخدمين والصلاحيات، network access، الداتا، والنسخ أو الاحتفاظ حسب خصائص الخدمة وإعداده.

<Box type="story" icon="🔄" title="نفس الداتا، خط فاصل مختلف">

تشغيل database على EC2 يخلي العميل يدير OS والـ engine. نقلها لخدمة database مُدارة ينقل طبقات أكتر لـ AWS، لكن users وnetwork access والداتا والـ configuration المتاح يفضلوا مسؤولية العميل.

</Box>

## AWS مش مسؤولة عن كل configuration

S3 bucket خاصة بالافتراضي في سيناريوهات كثيرة، لكن العميل مسؤول عن السياسات والـ public access وإعدادات المشاركة. وجود encryption feature لا يعني إنها مفعلة أو مناسبة تلقائيًا لكل workload.

كمان العميل مسؤول عن training والإجراءات والاستجابة داخل بيئته. AWS توفر خدمات وتقارير امتثال، لكن المؤسسة تقرر إذا تصميمها يحقق متطلباتها.

## مقارنة سريعة

- **EC2:** العميل يدير OS وpatching والتطبيق فوقه.
- **Managed database:** AWS تدير طبقات database/OS حسب الخدمة؛ العميل يدير الوصول والداتا والإعدادات المتاحة.
- **S3:** AWS تدير البنية والمنصة؛ العميل يدير data classification والسياسات والمشاركة والإعداد.
- **SaaS:** المزود يدير أغلب الـ stack؛ المؤسسة تدير accounts والمحتوى والـ configuration المتاح.

`Managed` معناها مسؤوليات أقل في طبقات محددة، مش انعدام مسؤولية العميل.
