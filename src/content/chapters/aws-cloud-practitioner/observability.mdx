## 🧠 افهم: تلات أسئلة بعد العطل

يوم الخميس الساعة ٩ بالليل، دُكّان بقى بطيء جدًا، وبعدين صور المنتجات اختفت. الفريق محتاج يجاوب تلات أسئلة مختلفة:

1. **إيه اللي بيحصل دلوقتي؟** الـ CPU كام؟ في errors؟ من إمتى؟ ← **CloudWatch**
2. **مين غيّر إيه؟** حد مسح حاجة؟ عدّل Security Group؟ ← **CloudTrail**
3. **الإعدادات بقت إيه، وهل مخالفة للقواعد؟** الـ bucket كان private وبقى public إمتى؟ ← **AWS Config**

وسؤال رابع للتطبيقات الموزعة: **الطلب ده اتأخر في أنهي خدمة بالظبط؟** ← **X-Ray**.

<Hl c="y">CloudWatch = صحة النظام وأداؤه (metrics وlogs وalarms). CloudTrail = سجل كل API call: مين عمل إيه وإمتى ومنين. Config = تاريخ الإعدادات وهل مطابقة للقواعد.</Hl>

<Box type="story" icon="🏪" title="المحل وكاميراته">

- **CloudWatch** زي **شاشة الكاشير** اللي بتوريك عدد الزباين ومبيعات الساعة، و**جرس** بيرن لو الطابور عدّى ١٠ أشخاص.
- **CloudTrail** زي **كاميرا المراقبة** على باب المخزن: بتسجل مين دخل، الساعة كام، وخد إيه.
- **Config** زي **جرد** بيصوّر الرفوف كل ما حاجة تتحرك، ويقولك «الرف ده مكانه غلط حسب القواعد».

</Box>

## 🔍 من جوه: كل أداة بالتفصيل

### Amazon CloudWatch

- **Metrics:** أرقام بوقت. خدمات AWS بتبعت metrics لوحدها (CPU للـ EC2، requests للـ ALB، errors للـ Lambda). الـ memory والـ disk جوه EC2 محتاجين **CloudWatch agent**. وتقدر تبعت **custom metrics** (عدد الطلبات المدفوعة مثلًا).
- **Logs:** سطور نصية من التطبيقات والخدمات في **log groups**. **Logs Insights** بيخليك تعمل queries عليها.
- **Alarms:** بتراقب metric، ولو عدّى حد لمدة معينة بتعمل action: SNS، Auto Scaling، أو EC2 action (reboot/recover).
- **Dashboards:** شاشة فيها الرسوم المهمة.
- وفي أدوات أكتر: **Synthetics** (زبون وهمي بيجرب الموقع كل دقيقة)، و**Application Signals** للتطبيقات.

### AWS CloudTrail

- بيسجل **API calls** على الحساب: مين (user/role)، عمل إيه (`DeleteBucket`)، إمتى، منين (IP)، ونجح ولا لأ.
- **Event history** بيحتفظ بآخر **٩٠ يوم** من management events مجانًا.
- عشان تحتفظ أكتر أو تحلل: اعمل **trail** يبعت لـ S3 (ولـ CloudWatch Logs)، أو **CloudTrail Lake** للـ queries.
- **Data events** (زي كل `GetObject` على S3) مش متسجلة افتراضيًا، وبتتحاسب لو فعّلتها.

### AWS Config

- بيسجّل **إعدادات** الموارد وكل تغيير فيها (configuration history).
- **Config rules:** «كل bucket لازم يكون Block Public Access مفعّل»، «كل EBS لازم يكون مشفّر». بيقولك compliant ولا لأ.
- ممكن يعمل **remediation** أوتوماتيك عن طريق Systems Manager.

### AWS X-Ray

**tracing** للطلب وهو بيعدي على خدمات كتير (API Gateway ← Lambda ← DynamoDB)، ويرسم **service map** فيها كل خدمة أخدت قد إيه وفين الـ errors. (AWS بتشجع الاتجاه لـ OpenTelemetry مع CloudWatch، راجع الـ docs.)

### AWS Health Dashboard

بيقولك لو في **مشكلة عند AWS نفسها** بتأثر على مواردك (AZ فيها مشكلة، maintenance مجدول). فيه صفحة عامة لحالة الخدمات، وجزء خاص بحسابك.

## 🛠️ طبّق: alarm وتحقيق لدُكّان

⚠️ CloudWatch فيه Free Tier (عدد alarms وmetrics وlogs). الـ alarm الواحد والـ SNS email في حدود التجربة.

1. **اعمل SNS topic** واشترك بإيميلك (أكّد الاشتراك من الإيميل):

```bash
aws sns create-topic --name dukkan-oncall
aws sns subscribe --topic-arn <TOPIC_ARN> --protocol email --notification-endpoint you@example.com
```

2. **اعمل alarm** على الـ Lambda بتاعة فصل ١٥ (أو أي instance):

```bash
aws cloudwatch put-metric-alarm --alarm-name dukkan-lambda-errors \
  --namespace AWS/Lambda --metric-name Errors \
  --dimensions Name=FunctionName,Value=dukkan-products \
  --statistic Sum --period 60 --evaluation-periods 1 \
  --threshold 1 --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions <TOPIC_ARN>
```

3. **فجّر error:** عدّل الكود وخلّيه يعمل `throw new Error("test")` واستدعيه. **المتوقع:** في خلال دقيقتين الـ alarm بيبقى `In alarm`، وإيميل بيوصلك.
4. **حقق بـ CloudTrail:** `CloudTrail` ← `Event history` ← فلتر `Event name = UpdateFunctionCode` أو حسب اسم الـ function. **المتوقع:** هتلاقي **إنت** اللي عدّلت الكود، الساعة كام، ومن أنهي IP.
5. **فكّر:** لو عايز تتأكد إن مفيش أي bucket في الحساب public **طول الوقت**، مش مرة واحدة، أنهي خدمة؟ (AWS Config rule).

🧹 **تنضيف:** رجّع كود الـ Lambda، امسح الـ alarm والـ SNS topic.

## ⚖️ قارن: التلاتة اللي بيتلخبطوا

| | CloudWatch | CloudTrail | AWS Config |
| --- | --- | --- | --- |
| السؤال | النظام **صحته** إيه؟ | **مين** عمل إيه؟ | الإعدادات **بقت** إيه؟ ومطابقة؟ |
| بيسجل | metrics وlogs | API calls | حالة الموارد وتغييراتها |
| مثال | CPU ٩٠٪ من ١٠ دقايق | سارة عملت `DeleteBucket` الساعة ٣ | الـ bucket ده بقى public من امبارح ومخالف |
| بيعمل | alarms، dashboards، scaling | audit، تحقيق أمني | compliance، تاريخ إعدادات |

| بيتلخبط مع | الفرق |
| --- | --- |
| X-Ray ↔ CloudWatch | X-Ray بيتتبع **طلب واحد** عبر الخدمات. CloudWatch بيجمّع **أرقام وlogs** |
| Health Dashboard ↔ CloudWatch | Health = مشاكل **عند AWS**. CloudWatch = حالة **مواردك** |
| CloudTrail ↔ VPC Flow Logs | CloudTrail = **API calls**. Flow Logs = **اتصالات الشبكة** |

<Box type="interview" title="الكلمات المفتاحية">

«monitor»، «metrics»، «alarm»، «logs»، «dashboard» ← **CloudWatch**.
«audit»، «who made the API call»، «governance»، «user activity» ← **CloudTrail**.
«configuration history»، «compliance with rules»، «resource inventory» ← **AWS Config**.
«trace requests»، «distributed application»، «bottleneck» ← **X-Ray**.

</Box>
