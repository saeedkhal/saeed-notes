## Incident في SaaS وقت الـ peak

شركة SaaS عندها `CloudFront → ALB → ECS → RDS Multi-AZ`. الساعة 10:00 الـ checkout latency طلعت من 250ms لـ 8s، وبعدها errors وصلت 12%.

1. الساعة 10:01، `CloudWatch Alarm` لاحظ إن `ALB 5XX` عدى 5% لمدة دقيقتين وبعت `SNS` للـ on-call.
2. الساعة 10:04، dashboard وضحت إن CPU طبيعية، لكن database connections عند الحد.
3. الساعة 10:07، `X-Ray trace` بيّن إن 7.4s من الـ request رايحين في database call.
4. الساعة 10:10، الفريق راجع `CloudTrail` ولقى deployment role غيّر task definition الساعة 09:58.
5. الساعة 10:14، `AWS Config` وضّح إن parameter اتغير عن الـ approved baseline.
6. الساعة 10:18، rollback رجّع latency لـ 280ms.

<Hl c="y">كل أداة جاوبت سؤال مختلف: حصل إيه؟ الطلب اتأخر فين؟ مين غيّر؟ والإعداد كان إيه؟</Hl>

## CloudWatch: حالة التشغيل دلوقتي

`CloudWatch` يجمع metrics وlogs، يبني dashboards، ويشغّل alarms. الـ metric رقم عبر الزمن؛ الـ log تفاصيل event؛ والـ alarm حالة مبنية على threshold أو expression.

الـ alarm نجح لأنه اكتشف symptom بسرعة. لكنه لوحده فشل في تحديد السبب. Threshold حساس جدًا يعمل noise، وحساس قليلًا يفوّت incident؛ اختار window وevaluation periods من سلوك الإنتاج.

## X-Ray: رحلة request واحدة

`AWS X-Ray` يتتبع request في تطبيق معمول له instrumentation ويقسم الزمن على services وdependencies. في المثال، trace فرّقت بين ALB bottleneck وECS code وRDS call.

X-Ray مش بديل للـ metrics: trace ممتازة للتفصيل، لكن CloudWatch أنسب لمعرفة إن 5% من كل الطلبات بطيئة.

## CloudTrail وConfig: الفعل والحالة

`CloudTrail` يسجل API activity من Console وCLI وSDK وخدمات AWS: principal، الوقت، source IP والـ action. استخدمه لسؤال: "مين نفذ `UpdateService`؟"

`AWS Config` يسجل configuration history للموارد المدعومة ويقيّمها ضد Config Rules. استخدمه لسؤال: "الـ security group كان مفتوح إمتى وهل خالف policy؟"

Config rule تبلغ عن noncompliance؛ مش بالضرورة تمنع أو تصلح التغيير إلا لو ربطت remediation. وCloudTrail مش application log.

## RTO وRPO: المطلوب قبل تصميم الـ DR

Fintech بتسجل عمليات دفع في `RDS`، والـ business قال: "لو Region وقعت، منقدرش نخسر أكتر من 5 دقايق transactions، والخدمة ترجع خلال 30 دقيقة."

- <En>RPO — Recovery Point Objective</En>: أقصى data loss مقبول زمنيًا. هنا `RPO = 5 minutes`.
- <En>RTO — Recovery Time Objective</En>: أقصى downtime مقبول من لحظة الانقطاع لرجوع الخدمة. هنا `RTO = 30 minutes`.

Timeline واقعي:

1. آخر replication مكتمل الساعة 14:02.
2. الـ Region فشلت الساعة 14:06.
3. المراقبة أعلنت incident الساعة 14:08.
4. الفريق فعّل recovery في Region تانية الساعة 14:20.
5. validation خلص و`Route 53` حوّل traffic الساعة 14:31.

الـ actual data loss أربع دقايق: **نجح RPO 5m**. الـ service رجعت بعد 25 دقيقة من 14:06: **نجح RTO 30m**.

لو آخر backup كان 13:55، يبقى data loss 11 دقيقة وRPO فشل حتى لو الخدمة رجعت بسرعة. ولو الداتا لحد 14:05 لكن الرجوع الساعة 14:50، RPO ينجح وRTO يفشل.

<Box type="idea" title="إزاي تختار strategy؟">

`Backup and restore` أرخص لكن RTO أطول. `Pilot light` يحتفظ بالـ core شغال. `Warm standby` يشغل نسخة أصغر ويقلل وقت الاسترجاع. `Multi-site active/active` أسرع وأغلى وأعقد، وبيحتاج حل consistency وfailover. المطلوب التجاري هو اللي يحدد، مش رغبتنا في أقوى architecture.

</Box>

CloudWatch alarms وAWS Health يساعدوا الاكتشاف؛ replication وbackups يحددوا نقطة الاسترجاع؛ runbooks والاختبارات يحددوا هل RTO واقعي. مجرد كتابة RTO/RPO مش ضمان—لازم DR drills تقيس الزمن والفقد الفعلي.
