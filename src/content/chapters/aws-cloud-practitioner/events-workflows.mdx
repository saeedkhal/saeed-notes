## المثال الأول: Refund خلال 30 دقيقة

Fintech تستقبل `RefundRequested`. الرحلة لازم تتحقق من المعاملة، تمنع duplicate، تطلب موافقة لو المبلغ فوق `$5,000`، تنادي payment provider، ثم ترسل email. الـ SLA هو `30 دقيقة`.

١. EventBridge rule تطابق `detail-type` وcurrency وتبدأ workflow.
٢. Step Functions تتحقق من idempotency ثم تعمل Choice حسب المبلغ.
٣. خطأ `5xx` من provider يتعمل له retry بـ backoff؛ خطأ validation يروح Catch فورًا.
٤. بعد النجاح، SES تبعت receipt، وevent منفصل يروح analytics.

## EventBridge: مين يهتم بالحدث؟

Event bus يستقبل events من AWS أو التطبيق أو SaaS integrations، والـ rules تعمل content-based matching إلى targets. استخدم schema/version واضح، ومتضعش card data أو secrets داخل event لمجرد سهولة النقل.

EventBridge routing مش workflow state. لو target فشل، صمم retries وDLQ/monitoring حسب التكامل، واعرف إن event delivery قد يتكرر.

## Step Functions: الرحلة تمشي إزاي؟

State machine تعرض steps وChoice وWait وParallel وRetry وCatch وتاريخ execution. ده أوضح من Lambda واحدة تنام وتخزن state بنفسها.

## Failure وtradeoff

الساعة `10:00` provider يرجع `503`. retries عند `10:00:01` و`10:00:03` و`10:00:07` تنجح في الرابعة. لو retry لكل error بما فيها `400`، workflow تضيع وقت وتكلفة من غير فرصة نجاح. حدد retryable errors وmax attempts وtimeout.

في distributed transaction، نجاح charge وفشل inventory يحتاج compensation مصممة؛ Step Functions تنسقها لكنها لا تجعل APIs الخارجية atomic.

## SES: البريد، مش الرحلة

SES للإرسال والاستقبال على scale. identities لازم تتوثق، والحساب قد يبدأ sandbox لحد production access. راقب bounces وcomplaints وsuppression، والتزم بسياسات spam. نجاح API call لا يضمن إن المستخدم قرأ الرسالة.

## 🧪 تمرين: Video approval workflow

ارسم upload event، virus scan، transcoding في فرعين، manual review لو content score فوق حد معين، publish، ثم email. اكتب timeout بالأرقام لكل خطوة، retryable errors، catch path، وcompensation لو publish حصل قبل اكتشاف فشل.
