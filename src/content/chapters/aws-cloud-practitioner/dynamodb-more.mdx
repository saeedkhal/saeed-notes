## المثال الأول: Cart لـ SaaS متعدد الـ tenants

المنصة عندها `2 مليون` مستخدم وذروة `45,000 request/s`. أهم طلبين: هات cart بـ `tenantId + userId`، وحدّث item بشرط إن version ما اتغيرتش.

١. partition key توزع tenants بدل ما كل traffic يروح لنفس partition.
٢. sort key تنظّم items أو snapshots حسب التصميم.
٣. conditional write تمنع overwrite متعارض.
٤. TTL تنظف sessions المؤقتة، لكن الحذف مش ضمان لحظي عند ثانية الانتهاء.
٥. CloudWatch يراقب throttling والـ latency والـ errors.

`DynamoDB` NoSQL serverless مُدارة، وبتحقق single-digit millisecond performance على scale لما المفاتيح والـ access patterns متصممين صح. `Scan` واسع في request ساخنة علامة إن model محتاج مراجعة.

## Capacity وميزات مهمة

On-demand يناسب traffic غير المتوقع، وprovisioned capacity يناسب تحكم وتوقع أوضح مع autoscaling حسب التصميم. GSI تضيف access pattern لكنها تضيف storage وwrite cost وقد يكون لها consistency behavior مختلف عن base table.

Streams تنشر تغييرات items، وGlobal Tables تدعم multi-Region active-active مع تصميم conflict والـ routing. Backup وPITR يحلوا recovery؛ Global Table وحدها مش backup من حذف منطقي.

## Cache: قلل `p95` من 180 إلى 20 ms

`ElastiCache` تدعم Valkey وMemcached وRedis OSS حسب الاختيار الحالي. في catalog API، أول request تعمل cache miss فتقرأ RDS في `180 ms` وتخزن النتيجة `60 ثانية`؛ الطلبات التالية ترجع في `20 ms`.

الفشل: price اتغير في المصدر لكن cache قديمة تعرض قيمة قديمة. الحل حسب المتطلب: TTL أقصر، invalidation event، أو عدم cache لمسار حساس. Cache miss لازم يرجع لمصدر الحقيقة؛ eviction مش data loss لو التصميم صح.

## مقارنة failure modes

- DynamoDB key ساخنة: throttling وتوزيع سيئ رغم إن الخدمة managed.
- ElastiCache miss storm: ضغط مفاجئ على source database.
- DocumentDB migration: feature مستخدمة غير متوافقة.
- Neptune: تكلفة وتعقيد بلا graph query حقيقية.
- Redshift: dashboards تضغط لو data loading أو model غير مناسب، لكنه مش OLTP replacement.

## 🧪 تمرين: Fintech access patterns
