## 🧠 افهم: الداتا بتروح فين لما السيرفر يقفل؟

برنامج المحاسبة على EC2 بيكتب ملفات كل يوم. سؤال: لو الـ instance وقفت أو اتمسحت، الملفات دي بتروح فين؟

ده بيعتمد على **الهارد اللي الملفات عليه**. الـ instance نفسها مجرد CPU وRAM. التخزين الدائم بيجي من **Amazon EBS (Elastic Block Store)**: هارد افتراضي متوصل بالـ instance عن طريق الشبكة، وبيفضل موجود حتى لو الـ instance وقفت.

<Hl c="g">EBS volume = هارد افتراضي دائم، بيتركب في instance في نفس الـ AZ. والـ snapshot = نسخة منه محفوظة بأمان تقدر تعمل منها هارد جديد في أي مكان.</Hl>

<Box type="story" icon="💾" title="الفلاشة والصورة">

- **EBS volume** زي **هارد خارجي** بتركّبه في اللابتوب. لو اللابتوب باظ، الهارد سليم وتركّبه في لابتوب تاني. بس لازم يكون **في نفس الأوضة** (نفس الـ AZ).
- **Snapshot** زي إنك تصوّر الهارد كله وتحط الصورة في **خزنة البنك** (S3). تقدر تعمل منها هارد جديد في أي أوضة أو أي فرع.
- **Instance store** زي **الـ RAM**: سريع جدًا، بس لما الجهاز يقفل اللي عليه بيروح.

</Box>

## 🔍 من جوه: التفاصيل اللي بتفرق

### حقائق أساسية

- الـ volume مربوط بـ **AZ واحدة**.
- عادةً متركّب في **instance واحدة** في نفس الوقت (في استثناء اسمه Multi-Attach لأنواع `io1/io2` وبشروط).
- الـ instance الواحدة ممكن يتركّب فيها **أكتر من volume**.
- تقدر **تكبّر** الحجم أو تغيّر النوع وهو شغال.
- بتدفع على **الحجم اللي حجزته** (GB في الشهر)، حتى لو فاضي، وكمان على الأداء الزيادة في بعض الأنواع.

### أنواع الـ volumes

| النوع | SSD/HDD | مناسب لـ |
| --- | --- | --- |
| `gp3` | SSD | الاختيار الافتراضي: OS، مواقع، databases صغيرة. تقدر تزود الـ IOPS لوحدها من غير ما تكبّر الحجم |
| `io2 Block Express` | SSD | databases حساسة محتاجة IOPS عالية جدًا وثابتة |
| `st1` | HDD | throughput كبير وقراية متتالية: logs، big data |
| `sc1` | HDD | أرخص حاجة، لداتا نادرًا ما بتتقري |

### Snapshots

- **Incremental:** أول snapshot بينسخ الـ blocks المستخدمة، واللي بعده بينسخ اللي اتغير بس. فبتدفع على الفرق.
- بيتخزن في S3 بتاع AWS (إنت مش بتشوف الـ bucket).
- **Amazon Data Lifecycle Manager** أو **AWS Backup** بيعملوا snapshots بجدول ويمسحوا القديم أوتوماتيك.

### التشفير

فعّل **EBS encryption by default** في الـ Region، وكل volume جديد هيتشفّر بمفتاح من **KMS** (فصل ٣٠). الـ snapshot من volume مشفّر بيبقى مشفّر.

## 🛠️ طبّق: backup واسترجاع لهارد المحاسبة

⚠️ volume صغير (`1 GiB`) وsnapshot بيتحاسبوا بمبالغ صغيرة جدًا، بس امسحهم بعد الـ Lab.

1. **اعمل volume:** `EC2` ← `Volumes` ← `Create volume` ← `gp3`، `1 GiB`، نفس AZ الـ instance بتاعتك (لو عندك واحدة من فصل ١٢)، tag `Project=dukkan-lab`.
2. **ركّبه (اختياري):** `Actions` ← `Attach volume` ← اختار الـ instance.
3. **اعمل snapshot:**

```bash
aws ec2 create-snapshot --volume-id vol-0123456789abcdef0 \
  --description "dukkan accounting backup" \
  --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Project,Value=dukkan-lab}]'
```

4. **استرجع في AZ تانية:** `Snapshots` ← اختاره ← `Create volume from snapshot` ← اختار AZ مختلفة.
   **المتوقع:** volume جديد بنفس الداتا في AZ تانية. ده إزاي «بتنقل» volume.
5. **فكّر:** لو عايز الـ backup ده يتعمل كل ليلة ويتمسح بعد ٧ أيام، هتستخدم إيه؟ (AWS Backup أو Data Lifecycle Manager).

🧹 **تنضيف:** detach وdelete للـ volumes، وdelete للـ snapshot.

## ⚖️ قارن: أنواع تخزين جنب الـ instance

| | EBS | Instance store | EFS (فصل ١٨) | S3 (فصل ١٧) |
| --- | --- | --- | --- | --- |
| النوع | block (هارد) | block (هارد محلي) | file (فولدر مشترك) | object |
| بيفضل بعد Stop؟ | **أيوه** | **لأ** | أيوه | أيوه |
| مربوط بإيه؟ | AZ واحدة | الجهاز نفسه | Region (أكتر من AZ) | Region |
| كام instance توصل له؟ | واحدة عادةً | واحدة | آلاف في نفس الوقت | أي حد عنده صلاحية |
| مناسب لـ | OS وdatabase على EC2 | cache وملفات مؤقتة | ملفات مشتركة بين سيرفرات | صور وbackups وملفات كبيرة |

«داتا مؤقتة وسريعة جدًا ومش مشكلة لو ضاعت» ← **Instance store**.
«هارد دائم لـ EC2 واحدة» ← **EBS**.
«أكتر من instance تقرا وتكتب نفس الملفات» ← **EFS**.
