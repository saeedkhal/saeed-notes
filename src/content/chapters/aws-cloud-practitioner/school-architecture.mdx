## المتطلبات قبل الرسم

متجر يعالج `300 order/s` طبيعيًا و`2,000 order/s` وقت الحملات. المطلوب:

- product pages عند `p95 < 200 ms`.
- checkout response خلال `700 ms`.
- لا duplicate charge حتى مع retries.
- email وanalytics ممكن يتأخروا `10 دقايق` من غير تعطيل الطلب.
- AZ failure ما توقفش الخدمة، وorder data لها RPO أقل من دقيقة.

## Flow 1: فتح الموقع في 140 ms

١. Route 53 يحل الاسم إلى CloudFront.
٢. CloudFront ترجع JavaScript والصور من edge لو cache hit؛ لو miss تجيبها من S3 origin خاصة.
٣. الـ customer يسجل الدخول عبر Cognito ويحصل على token.
٤. الواجهة تعرض catalog؛ personalized responses لا تتكيّش بسياسة عامة بالغلط.

CloudFront يقلل latency وorigin load، لكنه مش بديل authorization. S3 تفضل private، والوصول للـ origin بصلاحيات مخصصة.

## Flow 2: Checkout في 520 ms

١. الساعة `20:00:00.000` العميل يرسل `POST /orders` مع token و`idempotencyKey`.
٢. API Gateway تتحقق من route/authorizer وتطبّق throttling.
٣. Lambda تتحقق من tenant/customer والسعر الحالي.
٤. conditional write في DynamoDB تسجل order ومفتاح idempotency؛ retry بنفس المفتاح يرجع نفس النتيجة بدل charge جديد.
٥. response يرجع الساعة `20:00:00.520`.
٦. event يخرج للمسار الخلفي بعد ضمان عدم ضياعه وفق pattern مناسب؛ dual-write الساذج بين database وpublish خطر.

## Flow 3: شغل خلفي مستقل

SNS تعمل fanout إلى SQS queues للمخزون والإيميل والتحليلات. كل consumer عنده retries وDLQ وidempotency. لو email worker يقع `8 دقايق`، orders تفضل ناجحة والـ backlog يتعالج بعد رجوعه.

<Hl c="g">المسار المتزامن يخلص أقل قدر لازم لتأكيد الطلب؛ الشغل اللي يقبل التأخير يخرج لمسار durable غير متزامن.</Hl>

## Incident: حملة أكبر من المتوقع

- `20:00`: الحمل يصل `2,000 order/s`.
- `20:01`: Lambda توسع، لكن DynamoDB throttling يظهر بسبب partition key مركزة.
- `20:02`: API error rate تعدي `2%` والـ alarm يفتح incident.
- `20:04`: الفريق يفعّل mitigation المخطط ويقلل traffic؛ orders المقبولة محفوظة، والرسائل المتأخرة في queues.

الدرس: serverless scaling في طبقة لا يضمن capacity في الطبقة التالية. load test لازم يثبت keys والـ quotas والـ downstream قبل الحملة.

## Security وtradeoffs

- Cognito يدير user identity/tokens، لكن backend يتحقق من token والـ authorization لكل order.
- IAM roles أقل صلاحية لكل function/consumer، وتشفير وlogs بلا card secrets.
- WAF/controls مناسبة قد تحمي الـ edge/API، وbudgets تراقب requests وduration وcapacity والرسائل.
- DynamoDB اختيار تعليمي هنا؛ لو checkout يحتاج joins وmulti-row relational transactions، RDS/Aurora ممكن يكونوا أنسب.

<Box type="warn" title="Architecture مش قائمة خدمات">

كل مكوّن لازم يرتبط بمتطلب وفشل محدد. إزالة SNS أو Cognito أو DynamoDB ممكن تكون صح في نظام مختلف؛ القرار يتغير مع consistency والـ SLA والفريق والتكلفة.

</Box>

## 🧪 تمرين: Production review

غيّر المتطلبات إلى `5,000 order/s`، RTO `10 دقايق` لRegion failure، وتقارير تقبل تأخير ساعة. ارسم request/event flows، احسب concurrency لو Lambda مدتها `250 ms`، وحدد hot-key risk وDLQ alarm. بعدها اكتب game day: Region/AZ failure، duplicate request، email outage، وشرط نجاح رقمي لكل تجربة.
