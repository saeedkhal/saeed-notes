## 🧠 افهم: من سيرفر واحد لنظام بيستحمل رمضان

دُكّان بدأ بسيرفر واحد. دلوقتي المطلوب، بكلام عم حسن:

1. «الموقع يفتح بسرعة لزباين مصر والخليج.» ← **سرعة**
2. «لو حاجة وقعت، الزبون ميحسش.» ← **availability**
3. «متضيعش ولا طلب.» ← **durability**
4. «رمضان ×١٠ من غير ما حد يصحى.» ← **elasticity**
5. «داتا الزباين محدش يشوفها.» ← **security**
6. «الفاتورة تبقى على قد الشغل.» ← **cost**

كل requirement من دول اتحلت في فصل. الفصل ده بيركّبهم مع بعض، ويوريك إن كل خدمة **موجودة عشان سبب**.

<Hl c="u">المعمارية الكويسة مش أكتر خدمات. كل مكوّن لازم تقدر تقول «ده موجود عشان يحمي من كذا»، ولو مش قادر، شيله.</Hl>

<Box type="story" icon="🏗️" title="المطعم الكبير">

مطعم صغير فيه طباخ واحد بيعمل كل حاجة. لما يكبر بيبقى فيه: **بواب** على الباب (CloudFront/WAF)، **مضيف** بيوزّع على الترابيزات (ALB)، **جرسونات** كتير وبيتغيروا (containers)، **دفتر حسابات** محفوظ عند محاسب (Aurora)، **حامل أوردرات** للمطبخ (SQS)، و**مدير** بيراقب كل حاجة (CloudWatch). كل واحد ليه دور، ولو واحد غاب في بديل.

</Box>

## 🔍 من جوه: كل طبقة وبتحمي من إيه

| الطبقة | الخدمة | بتحل إيه | لو شلناها؟ |
| --- | --- | --- | --- |
| DNS | Route 53 | الاسم والتوجيه وfailover | مفيش اسم ثابت، ومفيش تحويل لـ Region تانية |
| Edge | CloudFront | سرعة للزباين البعيدين، cache، HTTPS | كل طلب بيسافر للـ Region |
| حماية | WAF + Shield | SQL injection، bots، DDoS | الهجمات توصل للتطبيق |
| Static | S3 (+ OAC) | صور وfrontend بمتانة عالية ومن غير سيرفر | السيرفرات تشيل حمل ملفات |
| توزيع | ALB في AZين | يوزّع ويستبعد العيّان | سيرفر واحد = نقطة فشل |
| تطبيق | ECS/Fargate + Auto Scaling | stateless، بيكبر ويصغر | تدير سيرفرات، ورمضان يوقّعك |
| طلبات | Aurora Multi-AZ | معاملات وjoins وfailover | تضيع طلبات أو توقف لو AZ وقعت |
| سلة | DynamoDB | قراية بالمفتاح بسرعة ثابتة | ضغط على Aurora |
| async | SNS → SQS → Lambda | الطلب ميستناش الإيميل | خدمة بطيئة توقّع الـ checkout |
| شبكة | VPC، private subnets، SGs | الـ database مش ظاهرة للإنترنت | سطح هجوم أكبر |

## 🛠️ طبّق: اتبع طلب، وكسّر حاجات

الـ Lab ورقي. خد ورقة وارسم الرسمة اللي فوق من الذاكرة الأول، وبعدين:

### ١. اتبع طلب «اطلب» خطوة خطوة

1. المتصفح يسأل Route 53 ← عنوان CloudFront.
2. CloudFront: WAF يفحص ← `/api/orders` مش متكيّش ← ALB.
3. ALB ← task سليم في أي AZ.
4. الـ task: يقرا السلة من DynamoDB ← يكتب الطلب في Aurora (transaction).
5. يعمل publish لـ `OrderPlaced` ← يرد على الزبون **فورًا** برقم الطلب.
6. في الخلفية: SQS ← Lambda تبعت الإيميل، وخدمة المخزن تحجز.

### ٢. سيناريوهات فشل: إيه اللي بيحصل؟

| اللي حصل | النتيجة المتوقعة |
| --- | --- |
| AZ a وقعت | ALB يبعت لـ AZ b، Auto Scaling يطلّع tasks هناك، Aurora يعمل failover. الزبون ممكن يحس ببطء ثواني |
| خدمة الإيميل وقعت ساعة | الرسايل مستنية في SQS، الطلبات شغالة عادي، الإيميلات توصل متأخرة |
| رمضان ×١٠ | Auto Scaling يزوّد tasks، CloudFront يشيل الصور، DynamoDB on-demand يكبر |
| bot بيعمل ١٠٠٠ طلب في الثانية | WAF rate-based rule يوقفه |
| موظف مسح جدول بالغلط | Aurora point-in-time recovery لقبلها بدقيقة |
| Region كلها وقعت | **الرسمة دي مش بتغطي ده.** محتاج DR في Region تانية (فصل ٤): هل الـ RTO يستاهل التمن؟ |

### ٣. الفاتورة

اكتب أغلى ٣ حاجات تتوقعها (غالبًا: Fargate tasks، Aurora، NAT Gateway/data transfer). وحط لكل واحدة فكرة توفير (Savings Plans، تصغير، VPC endpoints).

## ⚖️ قارن: تطور المعمارية

| | v1: البداية | v2: الرسمة دي | v3: لو كبرنا جدًا |
| --- | --- | --- | --- |
| Compute | EC2 واحدة | Fargate في AZين + Auto Scaling | + Regions متعددة |
| Database | على نفس السيرفر | Aurora Multi-AZ + DynamoDB | Aurora Global + DynamoDB global tables |
| Static | من السيرفر | S3 + CloudFront | نفس الشيء |
| Async | مفيش | SNS + SQS + Lambda | + EventBridge + Step Functions |
| Availability | لو وقع، وقع | يستحمل وقوع AZ | يستحمل وقوع Region |
| التكلفة والتعقيد | أقل حاجة | متوسط | عالي |
| مناسب لـ | تجربة الفكرة | معظم الشركات | خدمة عالمية حساسة |
