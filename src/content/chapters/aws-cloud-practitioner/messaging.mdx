## المثال الأول: Order confirmed

Checkout يستقبل `1,000 order/s`. إرسال email يأخذ `800 ms`، analytics أحيانًا تتوقف `20 دقيقة`، والمستخدم لازم يستلم response خلال `300 ms`.

١. checkout يحفظ order أولًا، ثم ينشر `OrderConfirmed`.
٢. SNS تعمل fanout إلى SQS queue للإيميل، queue للمخزون، وqueue للتحليلات.
٣. كل consumer يشتغل بسرعته؛ تعطل analytics لا يوقف checkout أو email.
٤. كل consumer يستخدم `orderId` كـ idempotency key لأن التسليم قد يتكرر.

## SQS: Buffer وضغط متحكم فيه

Standard queues قابلة للتوسع وتسليمها at-least-once، فالترتيب والتكرار لازم يدخلوا التصميم. FIFO تضيف ordering وdeduplication semantics ضمن حدودها، لكنها مش اختيار تلقائي لكل نظام.

`visibility timeout` يخفي message أثناء المعالجة. لو worker يحتاج `90 ثانية` والـ timeout `30 ثانية`، message ممكن تظهر لworker تاني قبل انتهاء الأول. اضبطه على زمن المعالجة أو جدده، مع idempotency دائمًا.

لو يدخل `1,000 msg/s` والعمال يخلصوا `700 msg/s`، backlog يزيد `300 msg/s`؛ بعد `20 دقيقة` يبقى `360,000` message. Queue تمنع السقوط الفوري لكنها لا تخلق capacity.

## SNS: Fanout

SNS publish/subscribe تدفع نسخة لكل subscription مطابقة: SQS أو Lambda أو HTTP/S أو email وغيرها. استخدم filter policies بحذر لتقليل traffic غير المطلوب، لكن راقب إن event schema والتصفية متوافقين.

## DLQ مش نهاية ناجحة

بعد `5` محاولات، message تالفة تدخل DLQ. alarm لازم يفتح incident، الفريق يصلح schema/consumer، يختبر message، ثم يعمل redrive بمعدل لا يعيد إسقاط النظام. حذف DLQ من غير تحقيق يخفي data loss.

<Box type="warn" title="Dual write ممكن يضيّع event">

لو التطبيق حفظ order ثم وقع قبل publish، الداتا موجودة والحدث ضاع. أنماط زي transactional outbox تعالج الفجوة؛ مجرد إضافة queue لا تجعل النشر atomic مع database.

</Box>

## 🧪 تمرين: احسب backlog

Video pipeline تستقبل `500 job/min`، وكل worker يعالج `20 job/min` وعندك `15 worker`. احسب نمو backlog في ساعة، واقترح scaling. أضف poison message، visibility timeout، DLQ alarm، وidempotency key يمنع إخراج الفيديو مرتين.
