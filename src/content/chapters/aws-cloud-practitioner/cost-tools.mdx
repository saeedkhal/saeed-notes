## قبل ولا بعد؟

أهم فرق: `Pricing Calculator` يعمل estimate قبل التنفيذ، و`Cost Explorer` يحلل تكلفة واستخدام حصلوا فعلًا ويعرض forecast.

<Box type="story" title="رحلة المدرسة">

قبل الرحلة تعمل ورقة تقدير للأتوبيس والأكل. أثناء الشهر تراجع كشف المصروفات. ولو قربت تعدي السقف، عايز جرس إنذار. دي Calculator وExplorer وBudgets.

</Box>

## AWS Pricing Calculator

تبني estimate لخدمات وRegions وإعدادات متوقعة وتشارك النتيجة. مفيد للمقارنة والـ business case، لكنه **مش فاتورة مضمونة**.

الـ usage الحقيقي، discounts، taxes، data transfer، نمو الداتا، وتغيّر الأسعار ممكن يغيروا الرقم. راجع assumptions وتاريخ التسعير.

## Cost Explorer

`AWS Cost Explorer` يعرض historical cost and usage، يفلتر ويجمع حسب service وaccount وRegion وtag وغيرها، ويعمل forecasts وrecommendations مدعومة حسب الحالة.

استخدمه لسؤال: "إيه اللي زوّد فاتورة الأسبوع ده؟" مش لسؤال: "كام سعر architecture لسه مبنيتهاش؟"

<Hl c="g">Calculator قبل الصرف؛ Explorer بعده ومعاه forecast.</Hl>

## AWS Budgets

`AWS Budgets` يعمل thresholds على cost أو usage أو coverage/utilization لبعض commitments، ويرسل alerts عبر قنوات مدعومة.

الـ alert مش معناه إيقاف الموارد تلقائيًا. فيه `Budget Actions` لحالات وإجراءات محددة وبصلاحيات محسوبة، لكن متعتمدش إن budget لوحده hard spending cap.

<Box type="warn" title="التنبيه ممكن يتأخر">

بيانات billing مش لحظية، والموارد تقدر تصرف بين القياس والتنبيه. للحساب التعليمي: فعّل MFA، alerts، وامسح الموارد بعد المعمل؛ متستناش budget ينقذك.

</Box>

## Data Exports وCUR 2.0

`AWS Data Exports` هو الطريق الحالي الموصى به لتصدير بيانات billing تفصيلية ومتكررة إلى S3. أهم table هو `Cost and Usage Report 2.0 (CUR 2.0)`.

CUR 2.0 عنده schema ثابت أكتر من Legacy CUR، وتقدر تختار أعمدة وصفوف بـ SQL وتحدد granularity. في أكتوبر ٢٠٢٦ ظهرت standardized cost/rate columns اختيارية لتوحيد تحليل purchase options.

`Legacy CUR` لسه اسم هتقابله في مواد قديمة، لكنه غير المسار الجديد الموصى به. الملفات التفصيلية مناسبة لـ Athena وQuickSight وتحليلات FinOps.

## Cost allocation tags

اعمل user-defined tag زي `Project=SchoolPortal` أو `CostCenter=Admissions`، وبعدين **فعّله** كـ cost allocation tag من Billing.

الـ tag مش بيظهر بأثر رجعي كامل على تكلفة حصلت قبل إضافته وتفعيله، ومش كل نوع مورد يدعم tags بنفس الطريقة.

## Consolidated billing

مع `AWS Organizations`، management account يدفع فاتورة مجمعة للـ member accounts. ده يسهل رؤية التكلفة، وقد يجمع volume usage ويشارك بعض خصومات commitments حسب قواعد AWS.

لكن كل account يفضل boundary منفصل للموارد والـ IAM. consolidated billing مش معناه إن users في حساب بقوا يدخلوا موارد حساب تاني.

<Box type="idea" title="حساب لكل بيئة">

المدرسة تعمل accounts للـ production والـ development وsecurity، وتجمع الفاتورة مركزيًا. فصل الحسابات يقلل blast radius، والـ tags تقسم المشاريع جوه الحساب.

</Box>
