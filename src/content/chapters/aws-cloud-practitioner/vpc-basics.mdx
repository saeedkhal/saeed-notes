## المثال الأول: Checkout في 3 tiers

المطلوب تطبيق في `2 AZs`: public ALB، app tasks خاصة، وRDS خاصة. الـ CIDR هو `10.20.0.0/16` ولازم نسيب مساحة لتوسع سنة.

١. public subnets: `10.20.0.0/24` و`10.20.1.0/24`.
٢. app subnets: `10.20.10.0/24` و`10.20.11.0/24`.
٣. data subnets: `10.20.20.0/24` و`10.20.21.0/24`.
٤. كل subnet داخل AZ واحدة فقط؛ توزيع الأزواج يحقق resilience لو AZ تعطلت.
٥. ALB وحدها تستقبل من الإنترنت؛ app وdatabase بلا route مباشر للـ IGW.

`Amazon VPC` شبكة افتراضية معزولة منطقيًا. `/16` أكبر من `/24` لأن prefix الأكبر يترك bits أقل للعناوين. خطط CIDRs من غير overlap لو متوقع ربط VPCs أو on-premises لاحقًا.

## Public وPrivate بيتحددوا بالـ route

الـ public subnet عندها route زي `0.0.0.0/0 → Internet Gateway`. المورد نفسه يحتاج public addressing مناسب وقواعد أمان تسمح. الـ private subnet ماعندهاش route مباشر للـ IGW؛ ممكن تخرج عن طريق NAT من غير inbound مباشر من الإنترنت.

## Request flow بالأوقات

- `12:00:00.000`: العميل يحل DNS ويصل لعنوان ALB العام.
- `12:00:00.030`: route والـ IGW يوصلوا packet للـ ALB في public subnet.
- `12:00:00.045`: ALB يختار healthy app target خاص.
- `12:00:00.080`: app يفتح اتصال database على private IP.
- `12:00:00.210`: response يرجع على الاتصالات القائمة.

الـ route table تختار next hop بأكثر route تحديدًا؛ هي مش firewall. Security Groups وNACLs تتحكم في السماح والمنع.

<Box type="warn" title="اسم subnet مش control">

Subnet اسمها `private-db` وعندها route مباشر لـ IGW ليست خاصة وظيفيًا. راجع routes وpublic addressing وقواعد الأمان، مش tags فقط.

</Box>

## Tradeoff التخطيط

`/28` صغيرة قد تستنفد IPs وقت autoscaling أو load balancer operations؛ `/20` واسعة قد تهدر address space وتعمل overlap مستقبلًا. اختار مساحة من توقع عدد ENIs والنمو، واعرف إن AWS تحجز عناوين داخل كل subnet.

## 🧪 تمرين: صمم شبكة SaaS

عندك `120` app task اليوم وقد تصل `600`، وقاعدتا بيانات، و2 AZs. اقترح VPC/subnet CIDRs، route table لكل tier، ومسار request. بعدها افترض فشل AZ-A: حدد الموارد والمسارات المطلوبة لاستمرار الخدمة، واكتب نقطة فشل لو كل NAT أو app في AZ واحدة.
