## Incident: key اتسربت في repository

فريق SaaS اكتشف الساعة `11:05` إن developer رفع access key إلى repository عامة. الـ key كانت long-term وعليها `AdministratorAccess`، فالفريق اضطر يتعامل مع أسوأ احتمال: قراءة الداتا أو تغيير أي resource.

لو نفس المهمة كانت role session مدتها ساعة، تسمح فقط بـ `s3:GetObject` على prefix محدد، أثر التسريب كان أصغر زمنيًا ووظيفيًا.

<Hl c="g">Least privilege يضيّق الـ action والـ resource والـ condition والمدة؛ مش مجرد اسم policy.</Hl>

## Timeline للاستجابة والتصحيح

1. **11:05:** secret scanning يكتشف الـ key.
2. **11:08:** الفريق يعطل credential ويبحث في CloudTrail عن استخدامها.
3. **11:20:** workload تنتقل إلى IAM role بtemporary credentials.
4. **12:00:** policy تبدأ بأفعال وموارد محددة في بيئة test.
5. **بعد ٧ أيام:** last accessed وAccess Analyzer يساعدوا في إزالة صلاحيات غير مستخدمة.

النجاح إن workload تكمل المهمة من غير credential ثابتة ومن غير صلاحيات جانبية. الفشل إن `AccessDenied` يتصلح بـ `Action: *` أو إن session قصيرة تفضل بصلاحيات إدارية.

## Temporary credentials أفضل

الـ role session بتطلع access key وsecret وsession token لهم مدة صلاحية. لما المدة تنتهي، البيانات تبطل حتى لو نسخة منها اتسربت.

ده يقلل الخطر مقارنة بـ long-term access keys، لكنه مش يلغيه: session مسروقة تشتغل لحد انتهاءها، فلازم صلاحياتها محدودة ومدة الجلسة مناسبة.

للـ workloads على AWS، اربط role بالخدمة بدل تخزين keys في الكود أو ملف `.env`. للبشر، استخدم federation ومسار دخول مركزي.

## IAM Identity Center للبشر

AWS IAM Identity Center يدي إدارة مركزية لوصول workforce لأكتر من AWS account وتطبيق. تقدر تستخدم مخزن هويات داخلي أو تربطه بمزود هوية خارجي، وتوزع permission sets على users وgroups وحسابات.

Identity Center مش بديل عن تصميم الصلاحيات؛ هو ينظم الدخول والتوزيع. Permission set واسع يفضل واسع.

## Permissions boundary: سقف مش منحة

Permissions boundary هي managed policy بتحط **الحد الأقصى** اللي identity-based policies تقدر تمنحه لـ IAM user أو role. هي لا تمنح permission لوحدها.

مثال: platform team تسمح لفريق منتج ينشئ roles لتطبيقاته، لكن boundary تمنع أي role جديد من تجاوز خدمات أو حدود معينة. ده يفيد تفويض إدارة الصلاحيات.

<Hl c="g">لو identity policy قالت Allow والـ boundary مش سامحة بالنطاق، الصلاحية الفعلية مش هتتمنح.</Hl>

وفيه طبقات تانية زي AWS Organizations SCPs. الـ SCP يحدد أقصى صلاحيات متاحة لحسابات المؤسسة؛ مش هو كمان grant مباشر.

## دورة تضييق الصلاحية بالأدلة

1. ابدأ من task واضحة وصلاحيات قليلة.
2. اختبر في بيئة غير إنتاجية.
3. راقب الاستخدام والطلبات المرفوضة.
4. استخدم أدوات زي IAM Access Analyzer ومعلومات last accessed كأدلة مساعدة.
5. شيل الصلاحيات غير المستخدمة وراجع دوريًا.

<Box type="warn" title="متصلحش AccessDenied بـ wildcard">

إضافة `Action: *` و`Resource: *` سريعة، لكنها تخفي السبب وتوسع أثر أي اختراق. اقرأ الحدث وحدد action وresource وcondition المطلوبة.

</Box>

## قارن الأدوات

- **Temporary credentials:** تقلل عمر السر؛ لا تضيق الصلاحية تلقائيًا.
- **IAM Identity Center:** ينظم workforce access وpermission sets عبر حسابات؛ لا يجعل الـ permission set ضيقة تلقائيًا.
- **Permissions boundary:** سقف لصلاحيات user أو role؛ لا تمنح access وحدها.
- **SCP:** سقف على حسابات أو OUs في Organizations؛ ليست grant.
- **Access Analyzer / last accessed:** أدلة للمراجعة، وليست قرارًا آليًا كامل السياق.

## 🧪 Lab آمن: صغّر صلاحية incident responder

صمم جلسة مدتها `45 دقيقة` لمهندس يحتاج يقرأ logs ويعيد تشغيل service واحدة في staging. حدد actions وresources وcondition، واكتب ٣ أشياء ممنوعة. بعدين وضح ماذا يحدث لو identity policy تسمح بفعل والـ boundary لا تسمح به.
