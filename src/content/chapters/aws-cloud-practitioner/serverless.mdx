## المثال الأول: Checkout وقت حملة

متجر متوقع ينتقل من `40 request/s` إلى `1,200 request/s` لمدة 10 دقايق. المطلوب إن `POST /orders` يرد خلال `500 ms`، يسجّل الطلب مرة واحدة، وما يفتحش آلاف الاتصالات على PostgreSQL.

١. `API Gateway` يستقبل HTTPS ويطبّق route وauthorization وthrottling.
٢. Lambda تتحقق من الطلب وتستخدم `idempotencyKey` عشان retry ما يعملش order تاني.
٣. العملية القصيرة تكتب في database أو تبعت شغل خلفي لـ SQS.
٤. CloudWatch يقيس duration وerrors وthrottles؛ alarm يشتغل لو error rate عدّت `1%` لخمس دقايق.

## Concurrency بالأرقام

لو متوسط execution هو `250 ms` والحمل `1,200 request/s`، الـ concurrency التقريبية هي `1,200 × 0.25 = 300`. لو الـ database تستحمل `80` connection بس وfunction بتفتح connection لكل execution، النجاح في scaling عند Lambda ممكن يبقى فشل للـ database.

الحلول تشمل connection pooling مناسب زي `RDS Proxy`، queue لتنعيم الحمل، و`reserved concurrency` لحماية downstream. Reserved concurrency كمان تعزل سعة function، لكنها ممكن تعمل throttling لو اتحددت أقل من المطلوب.

## Cold start والـ latency

لما Lambda تحتاج execution environment جديدة، أول invocation عليها وقت تجهيز إضافي. مش كل invocation cold، والأثر بيتغير حسب runtime وحجم package والتهيئة والشبكة.

`Provisioned Concurrency` تجهز environments مسبقًا وتقلل التذبذب، مقابل تكلفة إضافية. في checkout حساس، قارن `p95` و`p99` قبل وبعد؛ متدفعش للحل قبل ما القياس يثبت المشكلة.

## Event sources والـ retries

- API Gateway ينادي Lambda بشكل synchronous وينتظر response.
- S3 وEventBridge يقدروا يبدأوا processing بسبب event.
- Lambda تقرأ SQS على batches من خلال event source mapping.

مصدر الحدث بيحدد retry behavior. في معالجة دفعة SQS، failure ممكن يرجّع messages للظهور؛ لذلك كل write مالي لازم يبقى idempotent، والرسائل المستعصية تروح DLQ بعد عدد محاولات محسوب.

## حدود واختيار بديل

Lambda execution التقليدية حدها الأقصى `15 دقيقة` حتى أكتوبر 2026. فيه quotas للـ concurrency والـ payload والذاكرة والـ ephemeral storage؛ بعضها قابل للزيادة وبعضها مرتبط بنوع التكامل، فراجع docs الحالية.

## مقارنة سريعة

API Gateway يدير واجهة الـ API؛ Lambda تنفذ compute. Lambda scaling مش ضمان إن كل dependency هتتحمل. `Pay per use` مفيد للحمل المتقطع، لكنه مش وعد إن التكلفة أقل في كل workload.
