## المثال الأول: SaaS API وقت deploy

شركة SaaS عندها API داخل image حجمها `420 MB`. الحمل الطبيعي `12 task`، وكل task تستحمل `80 request/s`. المطلوب deploy إصدار جديد من غير downtime، وrollback خلال `5 دقايق` لو error rate عدّت `2%`.

١. CI تبني image مرة واحدة وتفحصها، ثم ترفع digest ثابت إلى `Amazon ECR`.
٢. `ECS service` تنشئ tasks جديدة من task definition الجديدة.
٣. `ALB` مايبعتش traffic غير بعد نجاح health checks.
٤. deployment يحتفظ بالعدد الأدنى من healthy tasks؛ CloudWatch alarm يوقف أو يرجع الإصدار حسب الإعداد.
٥. الداتا تفضل في RDS/S3، مش جوه filesystem الـ container المؤقت.

## أربع أسماء، أربع مسؤوليات

- الـ `image` package ثابت؛ الـ `container` process شغالة منه.
- `ECR` registry للصور، مش runtime.
- `ECS` و`EKS` orchestrators يقرروا placement والعدد والـ rollout.
- `Fargate` compute capacity مُدارة تشغّل ECS tasks أو EKS pods من غير إدارة nodes.

## ECS ولا EKS؟

<Grid2>
<Card title="ECS" c={2}>

AWS-native، task definitions وservices، وتكامل مباشر مع IAM وALB. مناسب لفريق عايز orchestration من غير تشغيل Kubernetes ecosystem.

</Card>
<Card title="EKS" c={4}>

AWS تدير Kubernetes control plane، والفريق يدير manifests والـ add-ons والسياسات والـ workloads. اختاره لو Kubernetes API أو أدواته أو portability requirement حقيقية.

</Card>
</Grid2>

شركة عندها `35` microservice وplatform team بتدير Kubernetes في أكتر من بيئة ممكن تبرر EKS. فريق من `4` مهندسين وعنده `3` APIs فقط غالبًا يستفيد من بساطة ECS؛ الشهرة مش requirement.

## Fargate ولا EC2 capacity؟

Fargate يقلل patching وcapacity planning للـ hosts، وتحدد لكل task CPU وmemory. EC2 capacity تدي تحكم أوسع في instance types والـ agents والـ utilization، وممكن تبقى أوفر لحمل ثابت بعد القياس، لكن الفريق مسؤول عن nodes وسعتها وتحديثها.

<Hl c="p">ECS/EKS يحددوا orchestration؛ Fargate/EC2 يحددوا compute اللي الـ workloads هتشتغل عليه.</Hl>

## Incident flow: task بتستهلك memory

الساعة `14:03` task تعدي memory limit وتتوقف. الساعة `14:03:20` ALB health check يشيلها من التوجيه. ECS يبدأ replacement، لكن لو image tag متحرك أو startup بياخد `4 دقايق`، التعافي يتأخر. الحل: digest ثابت، startup سريع، health checks مضبوطة، وdesired count موزع على AZs.

الـ orchestrator يعيد process، لكنه مش بيرجع state ضاعت من داخل container. استخدم persistent storage/database واكتب shutdown handling للطلبات اللي كانت شغالة.

## الأمان والتكلفة

- متحطش secrets في image أو environment محفوظة في source؛ استخدم Secrets Manager أو Parameter Store وصلاحيات task/pod.
- افحص base images وحدّثها، وافصل task execution role عن application task role.
- Fargate تتحاسب حسب الموارد والمدة، وEKS له رسوم cluster وموارد، وECR له storage وtransfer/requests حسب الاستخدام.

## 🧪 تمرين: خطط deploy واقعي

API عليها `600 request/s`، وكل task تستحمل `75 request/s`. احسب الحد الأدنى النظري، ثم زوّد headroom وفشل task واحدة. ارسم rolling deployment لإصدار جديد يحتاج `90 ثانية` عشان يبقى healthy. قارن ECS on Fargate مع EKS managed node group في: التشغيل، التحكم، وقت الفريق، والتكلفة.
