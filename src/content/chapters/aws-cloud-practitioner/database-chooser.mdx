## المثال الأول: منصة e-commerce واحدة، خمس احتياجات

المنصة تعالج `600 order/s`، عندها `10 مليون` session، catalog مرن، fraud graph، وتقارير على `4 سنين`. اختيار database واحدة لكل ده ممكن ينجح في البداية، لكنه غالبًا يفرض tradeoffs غير لازمة.

ابدأ بورقة requirements:

1. أهم reads/writes وشكل المفاتيح؟
2. هل transaction وconstraints وjoins لازمة؟
3. `p95` latency والـ throughput كام؟
4. هل stale read لمدة `30 ثانية` مقبولة؟
5. RTO وRPO والـ Region requirements؟
6. تكلفة التشغيل وخبرة الفريق؟

## Timeline لقرار سيئ

- `10:00`: الفريق يحط checkout events في Redshift لأن التقارير موجودة هناك.
- `10:15`: ingestion latency توصل `90 ثانية`، والعميل مش شايف order فورًا.
- `10:20`: retries تعمل duplicate records لأن مسار OLAP مش مصمم كـ transaction API.
- النتيجة: التقارير نجحت لكن تجربة التشغيل فشلت. الحل فصل OLTP source عن analytics pipeline.

## Polyglot له ثمن

كل service جديدة تضيف IAM وnetworking وbackup وmonitoring وon-call skill. ابدأ بأقل عدد يحقق الـ SLA، وافصل لما benchmark أو failure requirement يثبت الاحتياج.

<Hl c="y">قرار قوي يذكر access pattern ورقم SLA وسبب رفض البديل، مش اسم خدمة مشهور.</Hl>

<Box type="warn" title="احسب التكلفة الكاملة">

قارن compute/capacity وstorage وI/O وrequests والـ backups والـ transfer والحد الأدنى للتشغيل. Serverless لا تعني مجانية.

</Box>

## 🧪 تمرين: Architecture review

SaaS عندها: invoices تحتاج transaction، tenant settings تُقرأ بالمفتاح `30,000 مرة/ثانية`، dashboard تقبل تأخير `15 دقيقة`، وcache failure لازم ما يوقفش checkout. اكتب لكل workload خدمة، source of truth، consistency، RTO/RPO، وبديل مرفوض. بعدين احذف أي خدمة لا يدعمها requirement رقمي.

## قالب القرار

«هنختار **الخدمة** لأن access pattern هو **النمط** عند **الحجم/latency**، ونحتاج **recovery**. رفضنا **البديل** لأن **tradeoff قابل للقياس**».
