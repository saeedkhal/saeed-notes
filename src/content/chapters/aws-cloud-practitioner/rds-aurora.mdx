## المثال الأول: Fintech ledger

منصة مدفوعات تنفذ `250 transaction/s`. تحويل الرصيد لازم يخصم ويضيف في transaction واحدة، والـ RTO لعطل instance هو `5 دقايق`، والـ RPO لحذف منطقي هو `15 دقيقة`.

١. API تبدأ SQL transaction وتكتب ledger entry بمفتاح idempotency.
٢. `RDS PostgreSQL Multi-AZ` ينسخ بشكل متزامن للـ standby حسب نوع deployment.
٣. لو primary فشلت الساعة `12:00`، AWS تعمل failover والـ app تعيد الاتصال بالـ DNS endpoint.
٤. لو operator نفذ `DELETE` الساعة `14:10`، الحذف ممكن يتنسخ؛ الفريق يستخدم point-in-time restore إلى وقت قبل الخطأ ثم يسترجع الداتا المطلوبة.

## Managed وحدود المسؤولية

RDS تدير provisioning والـ patching والـ backups والـ failover حسب الإعداد. الفريق مسؤول عن schema والـ indexes والـ queries والـ users والـ secrets والسعة والـ maintenance windows.

المحركات تشمل PostgreSQL وMySQL وMariaDB وOracle وSQL Server وDb2، مع اختلاف Region والترخيص والخصائص. Relational مناسب للـ transactions والـ constraints والـ joins، مش لمجرد إن الداتا شكلها جداول.

## Multi-AZ مش Read Replica

<Grid2>
<Card title="Multi-AZ" c={2}>

High availability وfailover. في Multi-AZ DB instance التقليدي، الـ standby مش endpoint للقراءة العادية.

</Card>
<Card title="Read Replica" c={4}>

Read scaling، وغالبًا replication asynchronous. تقارير متأخرة ثواني قد تقبلها؛ شاشة رصيد لحظية قد لا تقبل stale read.

</Card>

فيه كمان `Multi-AZ DB clusters` بreader instances قابلة للقراءة؛ متعممش قاعدة الـ standby التقليدية على كل deployment. اقرأ اسم المنتج والـ architecture الحالية.

## Aurora

Aurora engine من AWS ومتوافق مع MySQL أو PostgreSQL، والـ cluster storage موزع عبر `3 AZs` وبيكبر تلقائيًا ضمن حدود الخدمة. فيه writer وAurora Replicas للقراءة والـ failover.

اختيار Aurora لازم يطلع من throughput والـ failover والـ compatibility والتكلفة. عبارة "Aurora أسرع" وحدها مش business case، والتوافق لا يعني إن كل extension أو behavior مطابق.

## Timeline لتعافي واقعي

- `09:00`: automated backup/PITR شغالين باحتفاظ `7 أيام`.
- `10:05`: migration script تحذف `18,000` row بالغلط.
- `10:08`: alarm يكشف هبوط المعاملات؛ الفريق يوقف writes المؤذية.
- `10:15`: يبدأ restore لقاعدة جديدة عند `10:04:30`.
- `10:55`: validation تخلص، ثم تُستخرج الصفوف أو يحصل cutover حسب الخطة.

الـ RPO اتحقق لو نقطة الاسترجاع قبل الخطأ متاحة. الـ RTO فشل لو المطلوب `30 دقيقة` والتعافي أخد `50`. Snapshot موجودة مش دليل إن الخطة ناجحة.

<Box type="warn" title="Replica تنقل الخطأ">

Read Replica تحل ضغط القراءة، لكنها مش backup مستقل تلقائيًا. حذف أو corruption منطقي ممكن ينتقل لها. والـ backup مش بديل failover سريع.

</Box>

## أمان وتكلفة

حط database في private subnets، اسمح من app security group فقط، واستخدم Secrets Manager أو حل أسرار مناسب. احسب instances وstorage وI/O والـ backups الزائدة والـ replicas والنقل؛ Multi-AZ وread replicas موارد إضافية.
