## Request حقيقي: خدمة الفواتير تقرأ ملفًا

خدمة `invoice-api` على EC2 محتاجة تقرأ template من bucket اسمه `company-invoices-prod`، لكن ممنوع تحذف ملفات أو تلمس buckets تانية. المطلوب مش «ادّيها S3 access»؛ المطلوب قرار دقيق على كل request.

AWS Identity and Access Management يحدد **مين** يعمل **إيه** على **أنهي resource** وتحت **أنهي conditions**. IAM خدمة عالمية للحساب، لكن الموارد المتحكم فيها قد تكون إقليمية.

## Request flow في ٦ خطوات

1. EC2 بتاخد role اسمها `InvoiceReaderRole`.
2. التطبيق يحصل على temporary credentials للجلسة، من غير key مخزنة في الكود.
3. يطلب action اسمها `s3:GetObject`.
4. المورد المطلوب object تحت prefix محدد في `company-invoices-prod`.
5. AWS تجمع السياسات والحدود المؤثرة وتبدأ من implicit deny.
6. `Allow` مطابق يمرر الطلب ما لم يوجد `Explicit Deny` مؤثر.

طلب `s3:DeleteObject` يفشل، وقراءة bucket تانية تفشل. ده نجاح للـ least privilege، مش عطلًا في IAM.

## Identity-based policy

تتربط بـ user أو group أو role، وتقول الهوية دي تقدر تعمل إيه. مثلًا role خدمة الفواتير تقرأ templates من bucket محدد.

الـ managed policy كيان مستقل ممكن يتربط بأكتر من هوية. الـ inline policy جزء مباشر من هوية واحدة. الاختيار له أثر في الإدارة وإعادة الاستخدام.

## Resource-based policy

تتربط بالمورد نفسه وتحدد مين يقدر يوصل له، زي S3 bucket policy. مفيدة خصوصًا للوصول بين حسابات أو لتجميع قواعد المورد في مكانه.

مش كل خدمة تدعم resource-based policies، وسلوك جمع السياسات يختلف مع cross-account وOrganizations. للمبتدئ: اجمع كل السياسات المؤثرة قبل ما تحكم.

الأصل إن الطلب مرفوض. يحتاج `Allow` ينطبق عليه، وأي `Deny` صريح مؤثر يغلب الـ allow. بعد كده فيه طبقات إضافية زي permissions boundaries وSCPs.

<Hl c="b">Policy مش معناها مستخدم؛ هي ورقة قواعد. والـ role مش group؛ هو هوية بتتعمل لها جلسة مؤقتة.</Hl>

## قارن القطع القريبة

- **User:** هوية طويلة العمر داخل IAM لحالة محددة؛ البشر يفضل لهم federation حاليًا.
- **Group:** يجمع IAM users لتطبيق policies؛ لا يعمل له sign-in أو assume.
- **Role:** هوية تُفترض وتنتج temporary session.
- **Identity-based policy:** تبدأ من الهوية وتصف المسموح لها.
- **Resource-based policy:** تتعلق بالمورد وتحدد principals المسموحين.
- **Explicit deny:** يغلب allow مؤثرًا على نفس الطلب.

## 🧪 تمرين آمن: حلل request

اكتب request لخدمة media تقرأ object تحت `uploads/processed/` فقط. حدد principal وaction وARN المورد وcondition محتملة. بعدين اختبر على الورق ٣ طلبات: قراءة صحيحة، حذف object، وقراءة prefix مختلف. اشرح success أو AccessDenied لكل واحدة.

<Box type="warn" title="Console access غير API access">

Password للـ Console وaccess keys للـ API نوعان مختلفان من credentials. وجود واحد لا يعني وجود التاني، والأفضل تجنب الطويلة العمر متى توفر role.

</Box>
