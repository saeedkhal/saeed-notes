## Incident: الموظف الإداري فقد الوصول

شركة SaaS عندها AWS account إنتاجي. الساعة `02:10` حصل خطأ في مزود الهوية ومنع الـ admins من الدخول، وفي نفس الوقت مطلوب تغيير إعداد حساب حساس لا ينفذه إلا root.

الـ root user عنده وصول كامل وغير مقيد لموارد الحساب، وبعض المهام الحساسة تحتاجه. عشان كده هو مش حساب الشغل اليومي؛ هو مسار استثنائي لازم يبقى محمي ومراقب.

## Timeline للـ break-glass

1. **02:12:** on-call يعلن incident ويثبت إن المسار الإداري العادي غير متاح.
2. **02:16:** شخصان معتمدان يوافقان على استخدام root حسب runbook.
3. **02:20:** يتم استرجاع password وMFA من وسيلتين محفوظتين منفصلتين.
4. **02:24:** root ينفذ المهمة المحددة فقط، من جهاز موثوق وجلسة مراقبة.
5. **02:31:** sign-out، ثم مراجعة logs وتسجيل السبب والنتيجة.
6. **اليوم التالي:** إصلاح مسار الدخول، مراجعة الإجراء، وتدوير أي secret لو تعرض.

النجاح إن الوصول تم في دقائق، بموافقة وتسجيل ومن غير تحويل root لحساب مشترك. الفشل إن MFA ضاع مع password، أو إن الفريق يستخدم root يوميًا فلا يقدر يميز الاستخدام الطارئ.

## أول خطوات الحماية

1. استخدم بريدًا مؤسسيًا مراقبًا، مش بريد موظف ممكن يمشي.
2. حط كلمة سر فريدة وطويلة في password manager موثوق.
3. فعّل MFA للـ root فورًا.
4. اختار MFA مقاومًا للتصيد زي passkey أو security key لما يكون مناسبًا.
5. جهّز هوية إدارية منفصلة للعمل المعتاد، وفعّل لها MFA.
6. راقب وسجّل أي استخدام للـ root، واعمل alert مناسب.

AWS تدعم تسجيل أكتر من MFA device لبعض سيناريوهات root؛ راجع الوثائق الحالية وخطة المؤسسة عشان تقلل خطر فقد جهاز واحد من غير ما توزع الوصول بلا ضبط.

## Break-glass: متطلبات قابلة للاختبار

Break-glass إجراء موثق لاستخدام صلاحية عالية لما المسار العادي يفشل. لازم يحدد:

- مين يوافق على الاستخدام ومين يحضر التنفيذ.
- فين بيانات الدخول وأجهزة MFA محفوظة بأمان.
- إمتى نعتبر الحالة طوارئ.
- إزاي نسجل السبب والخطوات، ونراجع الحدث بعدها.
- إزاي نختبر الإجراء من غير كشف الأسرار.

<Hl c="y">الطوارئ مش مبرر لهوية مشتركة مستخدمة كل يوم؛ هي مسار نادر، بموافقة، مراقب، ومختبر.</Hl>

## Access keys للـ root؟ لأ

Access key هي بيانات وصول برمجية. متعملش root access keys. لو لقيت واحدة موجودة، حقق في استخدامها وبعدين عطّلها واحذفها بخطة آمنة؛ متنسخش السر في ticket أو chat.

للتطبيقات والناس، استخدم roles وtemporary credentials حيثما أمكن. هنفصلهم في الفصلين الجايين.

<Box type="warn" title="الـ MFA مش عصا سحرية">

MFA يقلل خطر كلمة سر مسروقة، لكنه مش يصلح صلاحيات واسعة أو access keys مسربة أو session اتسرقت. الحماية طبقات: هوية، أقل صلاحية، logging، وتنبيه.

</Box>

## مهام root القليلة

بعض مهام الحساب والفوترة والأمان تحتاج root حسب نوع الحساب وإعداد Organizations. القائمة بتتغير، فراجع صفحة AWS الرسمية **Tasks that require root user credentials** وقت الحاجة بدل حفظ قائمة قديمة.

## مفاهيم قريبة

- **Root user:** هوية الحساب الأعلى صلاحية ومطلوبة لمهام قليلة.
- **Administrative role:** وصول يومي بصلاحيات إدارية مضبوطة وجلسة مؤقتة.
- **MFA:** عامل إضافي يقلل خطر password مسروقة؛ مش بديل عن least privilege.
- **Break-glass:** إجراء طوارئ كامل، مش مجرد مكان password.
- **Root access key:** credential برمجية طويلة العمر عالية الخطورة؛ متعملهاش.
