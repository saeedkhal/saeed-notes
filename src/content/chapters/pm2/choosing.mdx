## المقارنة اللي تهمك

| السؤال | Fork mode | Cluster mode |
|---|---|---|
| نفس الـ port؟ | لأ بين نسخ HTTP العادية | أيوه |
| استغلال cores؟ | يدوي مع ports وLB | workers بسهولة |
| Node فقط؟ | يشغّل لغات وبرامج مختلفة | لتطبيقات Node الشبكية |
| reload تدريجي؟ | restart عادي غالبًا | `pm2 reload` |
| process رئيسية؟ | كل instance تطبيق مستقل | PM2 يدير cluster workers |
| memory مشتركة؟ | لأ | برضه لأ |

الـ overhead بتاع primary process موجود، لكن القرار الحقيقي مش كام MB زيادة؛ القرار مين هيوزع الشبكة ومين مسؤول عن lifecycle.

## Docker وKubernetes

في VPS واحدة، PM2 Cluster طريق بسيط لاستغلال cores. في Kubernetes، النمط الشائع process واحدة في كل container وreplicas متعددة:

<Flow items={[{"t": "Pod 1", "s": "Node process", "c": 1}, {"t": "Pod 2", "s": "Node process", "c": 2}, {"t": "Pod 3", "s": "Node process", "c": 3}, "←", {"t": "Service", "s": "load balancing", "c": 5}]} />

كده الـ orchestrator يدير health checks وrestarts وrolling updates. Cluster داخل كل container ممكن يبقى قرار مقصود، لكنه يضيف طبقة scaling ومراقبة ثانية. متعملوش تلقائيًا.

## الشغل CPU-heavy

لو request واحدة بتعمل image processing أو loop حسابية تقيلة، إضافة cluster تخلي requests مختلفة تتوزع، لكنها لا تسرّع الطلب الواحد.

استخدم:

- `worker_threads` لتوازي JavaScript CPU work داخل التطبيق.
- job queue وworker services للشغل الطويل.
- process منفصلة لو العزل أهم.

<Box type="interview" title="الإجابة العملية">

"VPS عليها API Node وعايز كل cores؟" — Cluster مع app stateless واختبار graceful reload. "Kubernetes؟" — ابدأ process واحدة لكل container وscale replicas. "سكريبت أو Python؟" — Fork.

</Box>
