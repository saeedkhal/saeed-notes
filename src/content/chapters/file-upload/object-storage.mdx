## نطلّع الملفات بره السيرفر

بدل الديسك، السيرفر يرفع الملف على **object storage** زي Amazon S3 أو Azure Blob Storage أو Google Cloud Storage. دي خدمات متخصصة في الملفات: إنت ترفع، وهي تهتم بالمساحة والنسخ (replication) والتوافر.

```ts
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { randomUUID } from "node:crypto";

const s3 = new S3Client({ region: process.env.AWS_REGION });

app.post("/files", requireAuth, upload.single("file"), async (req, res) => {
  const key = `users/${req.user.id}/${randomUUID()}`;
  await s3.send(new PutObjectCommand({
    Bucket: process.env.BUCKET,
    Key: key,
    Body: fs.createReadStream(req.file!.path),
    ContentType: req.file!.mimetype,
  }));
  const file = await db.file.create({ data: { ownerId: req.user.id, key, name: req.file!.originalname } });
  res.status(201).json({ id: file.id });
});
```

## بس استنى… الملف لسه بيعدّي من السيرفر

في الـ upload: من الـ client للسيرفر، ومن السيرفر لـ S3. وفي الـ download: نفس الحكاية بالعكس. يعني كل بايت بيعدّي **مرتين**، والسيرفر بيدفع التمن:

| المورد | بيروح فين |
| --- | --- |
| Bandwidth | كل ملف بيدخل ويخرج من السيرفر |
| Memory | buffers للملفات، ولو مش بتعمل stream ممكن الملف كله يتحمّل |
| CPU و connections | connection مفتوح طول ما ملف ٢ جيجا بيترفع على نت بطيء |

<Hl c="o">السيرفر لسه هو الـ bottleneck</Hl>، حتى لو الـ storage بقى scalable. ١٠٠٠ مستخدم بيرفعوا فيديوهات في نفس الوقت = السيرفرات كلها مشغولة بنقل بايتات، مش بالـ business logic.
