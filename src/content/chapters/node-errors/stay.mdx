## طلب واحد مش بيطفّي السيرفر

السيرفر فضل شغال، والغلط اتمسك جوه الـ handler، والرد كان `500` والنص `bad request`، والعملية خرجت `0` بعد ما السيرفر اتقفل بإيدينا.

```js
const server = http.createServer(async (req, res) => {
  try {
    throw new Error("bad request");
  } catch (e) {
    res.writeHead(500);
    res.end(e.message);
  }
});
```

<Hl c="g">حدود الـ try هنا الطلب، مش عمر العملية.</Hl> يوزر بعت JSON بايظ، أو صف مش موجود، أو قاعدة رفضت استعلام: رد واضح، وسجّل السبب، وكمّل تستقبل طلبات.

نفس الفكرة بره HTTP: دالة بتتعامل مع رسالة واحدة من الطابور تتمسك لوحدها. الرسالة تقع، والمستهلك يفضل شغال أو يرجّع الرسالة للطابور، مش يقتل العملية كلها.

## اخرج لما الحالة مش مضمونة

قفّل العملية (بكود غير صفر) لما:

- الاستثناء طلع من غير `catch` في مسار مش تابع لطلب واحد.
- الاتصال بقاعدة البيانات وقع والبرنامج مش عارف يشتغل من غيره.
- فشل وانت بتفتح البورت، بعد ما سجّلت `EADDRINUSE`.
- لسه في `unhandledRejection`. دي علامة إن فيه مسار نسيانه، ومش وضع طبيعي تعيش فيه.

متستناش `catch` فاضي. بلع الخطأ بيخلّي العملية شغالة وانت فاكرها سليمة، والطلب التالي يشتغل على حالة نص مكسورة.

## الخروج المرتب

إشارة `SIGTERM` أو `SIGINT` معناها "قفّل بهدوء": بطّل تقبل طلبات جديدة، استنى اللي شغّال، اقفل السيرفر وقاعدة البيانات، وبعدين اخرج. `SIGTERM` اتقاس بخروج `143` لما مفيش مستمع. لو عملت المستمع وقفيت بإيدك، تقدر تخرج `0` بعد ما القفل يخلّص، لأن الإيقاف نفسه كان مطلوب.

مدير العمليات (PM2 أو systemd أو Docker) هو اللي يرجع العملية بعد كود غير صفر. متبنيش جوه `uncaughtException` حلقة تكمّل الشغل.
