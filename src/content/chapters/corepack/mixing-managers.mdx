## كل مدير له عقد وطريقة بناء

لو مشروع معمول بـ npm وصاحبك شغّل Yarn أو pnpm، هو مش بس غيّر اسم الأمر. كل مدير عنده lockfile وطريقة تثبيت:

<Grid2>
<Card title="npm" c={1}>

يكتب `package-lock.json` ويبني `node_modules` بالطريقة اللي npm متوقعها.

</Card>
<Card title="Yarn" c={2}>

يكتب `yarn.lock`. بعض إصداراته تقدر تستخدم Plug'n'Play بدل `node_modules`.

</Card>
</Grid2>

<Card title="pnpm" c={3}>

يكتب `pnpm-lock.yaml`، ويستخدم content-addressable store وروابط بدل نسخ كل حزمة لكل مشروع.

</Card>

## إيه المشكلة العملية؟

تخيل المستودع فيه `package-lock.json`. صاحبك تجاهله وشغّل `pnpm install`:

1. pnpm يحل الحزم بقواعده.
2. يكتب `pnpm-lock.yaml`.
3. يبني layout مختلف.
4. بقى عندك ملفا قفل، ومفيش إجابة واحدة لسؤال: "أنهي شجرة هي الرسمية؟"

ممكن التطبيق يشتغل عنده ويقع عندك بسبب `peer dependency` مختلفة، أو import كان متاح بالصدفة مع hoisting مدير ومش متاح مع مدير تاني. والـ CI ممكن يقرأ lockfile غير اللي المطور اختبره.

<Box type="warn" title="متعملش commit لأكتر من lockfile">

اختار مدير واحد. احتفظ بالـ lockfile بتاعه، واحذف الباقي بعد ما تتأكد إنهم مش مقصودين. وجود `package-lock.json` و `yarn.lock` و `pnpm-lock.yaml` مع بعض غالبًا علامة إن الفريق ملوش اتفاق.

</Box>

## حتى نسختين من نفس المدير ممكن يختلفوا

npm ٨ وnpm ١١ مش شرط يكتبوا نفس صيغة القفل أو يحلوا الـ peers بنفس السلوك. نفس الكلام بين major versions من pnpm. عشان كده الاتفاق محتاج:

## طب ما نخلي README يقول؟

اكتبها في README، لكن النص مش enforcement. حد ممكن ينسى ويكتب `npm install`. حقل `packageManager` يخلي الاتفاق machine-readable، وCorepack يقرأه قبل تشغيل المدير.

<Box type="interview" title="سؤال إنترفيو">

"ينفع أفتح مشروع npm بـ pnpm؟" — تقنيًا ممكن في حالات، لكنك غيّرت resolver والـ lockfile والـ layout. من غير migration مقصودة من الفريق، ده تغيير في المشروع مش مجرد أداة محلية.

</Box>
