عندك branch اسمه `feature/cart`، وفي نفس الوقت زمايلك رفعوا commits جديدة على `main`. عايز تجمع الشغلتين. Git بيدّيك طريقتين، والاتنين **بيوصلوا لنفس الكود في الآخر**. الفرق كله في **شكل التاريخ**.

<Hl c="o">merge بيحافظ على التاريخ زي ما حصل، ويضيف commit بيربط الطريقين. rebase بيعيد كتابة الـ commits بتاعتك كأنك بدأت شغلك من آخر main</Hl>.

## نقطة البداية

```text
A ← B ← C ← D        ← main
     ↖
       E ← F         ← feature/cart
```

إنت بدأت من `B` وعملت `E` و `F`. وفي نفس الوقت `main` اتحرك لـ `C` و `D`.

## الـ merge

```bash
git switch feature/cart
git merge main
```

```text
A ← B ← C ← D ←─────── M   ← feature/cart
     ↖                 ╱
       E ← F ─────────
```

Git عمل commit جديد اسمه `M` (merge commit)، وليه **اتنين parents**: `D` و `F`. الـ commits بتاعتك `E` و `F` زي ما هي، بنفس الـ hashes.

### الـ fast-forward

لو `main` **متحركش** من ساعة ما بدأت، مفيش طريقين أصلًا:

```text
A ← B                ← main
     ↖
       E ← F         ← feature/cart
```

`git switch main && git merge feature/cart` هنا مش بيعمل merge commit. بيزق `main` لقدام لحد `F` وخلاص. ده اسمه **fast-forward**. ولو عايز merge commit حتى في الحالة دي، عشان يفضل باين إن ده كان feature لوحده، استخدم `git merge --no-ff`.

## الـ rebase

```bash
git switch feature/cart
git rebase main
```

```text
A ← B ← C ← D        ← main
              ↖
                E' ← F'   ← feature/cart
```

Git شال `E` و `F`، وعمل commits جديدة `E'` و `F'` **فوق `D`**، فيها نفس التعديلات. كأنك بدأت شغلك النهارده من آخر `main`.

<Box type="warn" title="E' مش E">

`E'` فيه نفس التعديل، بس الـ parent بتاعه اتغير (بقى `D` بدل `B`)، فالـ hash اتغير. فاكر من فصل ١؟ أي تغيير في الـ commit يعني commit جديد. يعني الـ rebase **بيعيد كتابة التاريخ**.

</Box>

- التاريخ مبقاش بيقول اللي حصل بالظبط.

## القاعدة الذهبية

<Box type="warn" title="متعملش rebase لـ commits حد تاني عنده">

لو الـ branch اترفع وحد تاني سحبه وبنى عليه، وإنت عملت rebase، الـ commits اللي عنده (`E` و `F`) مبقتش موجودة عندك (بقت `E'` و `F'`). لما يعمل pull، Git هيشوفهم commits مختلفة، والتاريخ هيتلخبط عنده وممكن التعديلات تتكرر.

يعني: **rebase على commits لسه عندك إنت بس. merge على أي حاجة مشتركة**.

</Box>

### طب لو عملت rebase لـ branch أنا رفعته؟

لو الـ branch بتاعك لوحدك (زي feature branch محدش شغال عليه غيرك)، عادي. بس الـ push العادي هيترفض، لأن التاريخ اللي على GitHub مختلف عن بتاعك. هنا محتاج force:

```bash
git push --force-with-lease
```

`--force-with-lease` أأمن من `--force`. بيرفض الـ push لو حد رفع حاجة جديدة على الـ branch من آخر مرة عملت fetch. يعني مش هتمسح شغل حد من غير ما تاخد بالك.

## `git pull` بيستخدم أنهي واحد؟

`git pull` = `fetch` + دمج. لو عندك commits محلية ومحدش رفع حاجة، الدمج بيبقى fast-forward. لو الاتنين اتحركوا، بيعمل merge commit، وده سبب commits زي "Merge branch 'main' of github.com/..." اللي بتملى التاريخ.

لو عايز `pull` يعمل rebase بدل كده:

```bash
git pull --rebase
# أو خليه الافتراضي
git config --global pull.rebase true
```

ده آمن، لأنه بيعمل rebase للـ commits المحلية بتاعتك بس، اللي لسه مترفعتش.

## الـ squash merge

في GitHub، لما تدوس "Squash and merge" على pull request، كل الـ commits بتاعة الـ feature بتتجمع في commit واحد على `main`. كده `main` بيفضل نضيف، commit لكل feature، حتى لو جوه الـ branch كان فيه 20 commit زي "fix typo" و "wip".

## تختار إزاي؟

<Box type="tip" title="الطريقة الشائعة في الفرق">

- وإنت شغال على الـ feature branch بتاعك لوحدك: `git pull --rebase` أو `git rebase main` عشان تفضل فوق آخر `main`.
- لما الـ feature تخلص: pull request، وتدخل `main` بـ merge أو squash، حسب اللي الفريق متفق عليه.
- على `main` أو أي branch مشترك: **ممنوع rebase**.

أهم حاجة إن الفريق كله يمشي على نفس الطريقة.

</Box>
