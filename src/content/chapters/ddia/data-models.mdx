## Relational vs Document

الموديل العلائقي (اقترحه Codd سنة 1970): داتا في <En>relations</En> (جداول) فيها <En>tuples</En> (صفوف). كسب ضد الـ hierarchical والـ network models وفضل مسيطر 30 سنة تقريبًا.

<strong>NoSQL</strong> ظهرت (الاسم أصلًا كان هاشتاج لميت-أب 2009!) لأسباب: محتاجين scalability أكبر (كتابات كتير، داتا ضخمة)، تفضيل للـ open source، استعلامات متخصصة، وزهق من قيود الـ schema. والمستقبل غالبًا <En>polyglot persistence</En>: كذا نوع داتابيز جنب بعض.

### مشكلة الـ Impedance Mismatch

الكود بتاعك بيفكر بـ objects، والداتابيز بتفكر بجداول — ومحتاج طبقة ترجمة (ORM زي Prisma/Hibernate) ومع ذلك مش بتخفي الفرق كله.

<Box type="story" title="مثال: بروفايل LinkedIn" icon="🍽️">

بروفايل فيه اسم + لستة وظايف + لستة تعليم + بيانات تواصل. ده <strong>شجرة</strong> (one-to-many). في SQL هتحطه في كذا جدول وتعمل joins، أو تحطه JSON في عمود. في Document DB هو مستند JSON واحد — <strong>locality</strong> أحسن: query واحدة تجيب كل حاجة.

</Box>

### Many-to-One و Many-to-Many — هنا بتبان القصة

ليه نخزن `region_id` بدل اسم المدينة نص؟ عشان <Hl c="y">Normalization</Hl>: معلومة ليها معنى بشري تتخزن مرة واحدة بس، ومن غيرها:

<Chips items={["نفس الإملاء في كل مكان", "مفيش التباس", "تعديل في مكان واحد", "دعم الترجمة/اللغات", "بحث أحسن"]} />

بس الـ normalization محتاج <strong>many-to-one</strong> relationships = joins. والـ document DBs دعمها للـ joins ضعيف، فالجوين بيتنقل لكود الأبلكيشن. ومع الوقت الداتا بتبقى مترابطة أكتر (الشركة تبقى entity ليها صفحة، التوصيات تشاور على يوزرز…) — يعني many-to-many.

<Box type="idea" title="التاريخ بيعيد نفسه">

نفس الجدل حصل في السبعينات: <En>IMS</En> من IBM كان hierarchical (شجرة زي JSON) ونفس المشكلة: many-to-many صعبة. اتقدم حلّين:

- <strong>Network model (CODASYL):</strong> كل record ليه أكتر من parent، والوصول بـ"access paths" زي pointers — لازم تمشي في السلسلة بإيدك. كود معقد ومش مرن.
- <strong>Relational:</strong> الداتا جداول مكشوفة، و<strong>query optimizer</strong> هو اللي بيختار الـ access path. تضيف index جديد والكود مايتغيرش. ده اللي كسب.

والـ document DBs النهارده رجعت للهيراركي في حتة الـ nesting، بس في many-to-one بتستخدم references (document reference) شبه الـ foreign key.

</Box>

<Box type="tip" title="Schema-on-read vs Schema-on-write">

"Schemaless" ده اسم مضلل. الأدق:

- <strong>Schema-on-write (SQL):</strong> الـ schema صريحة والداتابيز تفرضها — زي <strong>static typing</strong>.
- <strong>Schema-on-read (Document):</strong> الـ schema ضمنية والكود بيفسّرها وهو بيقرأ — زي <strong>dynamic typing</strong>.

مثال: عايز تقسم `name` لـ `first_name`: في document تكتب كود يتعامل مع القديم والجديد. في SQL تعمل `ALTER TABLE` + `UPDATE` (الـ UPDATE على جدول ضخم ممكن يبقى بطيء، والـ ALTER في معظم الداتابيز سريع — ماعدا MySQL القديمة اللي كانت بتنسخ الجدول كله). Schema-on-read مفيد لما الداتا heterogeneous فعلًا (أنواع كتير أو داتا جاية من برّه مش بإيدك).

</Box>

<Box type="idea" title="Locality مش ببلاش">

الداتابيز بتحمّل المستند كله حتى لو عايز حتة صغيرة، وأي تعديل بيحتاج إعادة كتابة المستند كله غالبًا. فخلي المستندات صغيرة وماتعملش writes بتكبّرها. والفكرة دي مش حكر على الـ document DBs: Spanner بيعمل interleaving للصفوف، Oracle عنده multi-table clusters، وBigtable/Cassandra عندهم column families.

</Box>

<strong>التقارب:</strong> Postgres و MySQL بقوا يدعموا JSON، و RethinkDB/MongoDB بقوا يدعموا نوع من الـ joins. <Hl c="g">الموديلين بيقربوا من بعض</Hl>، والهجين هو المستقبل.

## لغات الاستعلام: Declarative vs Imperative

<Grid2>
<Card title="Imperative (كود عادي)" c={4}>

بتقول للكمبيوتر <strong>إزاي</strong> يعمل الحاجة خطوة بخطوة (loop على الصفوف وفلترة).

</Card>
<Card title="Declarative (SQL)" c={3}>

بتقول <strong>عايز إيه</strong> (الشروط والشكل)، والـ optimizer يقرر إزاي.

</Card>
</Grid2>

مميزات الـ declarative: أقصر وأسهل، بيخبي تفاصيل التنفيذ فالداتابيز تقدر تحسّن نفسها من غير ما تغير الكويري، ومش بيحدد ترتيب، فـ <Hl c="b">سهل يتعمل parallel</Hl> على كذا core/ماكينة.

<Box type="story" title="مثال من الويب (هتحبه كفرونت-إند)" icon="🍽️">

CSS selector زي `li.selected > p` ده declarative: بتوصف إيه اللي عايز تلوّنه، والبراوزر يتصرف — ولو الكلاس اتشال اللون بيتشال لوحده. لو عملتها بـ JS imperative (`getElementsByTagName` + loop + `style.backgroundColor`) هتبقى أطول، ولو الكلاس اتشال اللون هيفضل، وماينفعش البراوزر يستفيد من API أسرع. نفس الفكرة بالظبط بتاعة React (declarative UI) vs jQuery!

</Box>

### MapReduce Querying

نموذج في النص: مش declarative بالكامل ولا imperative بالكامل. بتكتب دالتين `map` و `reduce` (لازم يكونوا <En>pure functions</En>: من غير side effects ولا queries إضافية) والفريمورك بيوزعها. MongoDB كان عنده MapReduce بس بعد كده عمل <En>aggregation pipeline</En> declarative (JSON-based) — يعني رجعوا لحاجة شبه SQL. 😄

## الـ Graph Models

لو أغلب علاقاتك many-to-many، الجراف هو الطبيعي: <strong>Vertices</strong> (عُقد) و <strong>Edges</strong> (علاقات). أمثلة: سوشيال نتورك، صفحات الويب واللينكات، الطرق والخرايط. وكمان ممكن تخزن أنواع مختلفة في نفس الجراف (فيسبوك: ناس، أماكن، events، checkins، كومنتات).

| الموديل | التكوين | اللغة |
|---|---|---|
| <strong>Property Graph</strong> (Neo4j, Titan) | كل vertex: id + edges داخلة/خارجة + properties (key-value). كل edge: id + tail + head + label + properties. | <strong>Cypher</strong> (declarative): `(a)-[:BORN_IN]->(b)`. وممكن تعمل نفس الحاجة في SQL بـ `WITH RECURSIVE` بس الكويري بتطلع طويلة جدًا (≈ 4 سطور Cypher قصاد 29 سطر SQL). |
| <strong>Triple-Store</strong> (Datomic, AllegroGraph) | كل حاجة جملة من 3 أجزاء: `(subject, predicate, object)` زي (جيم، بيحب، موز). الـ object إما قيمة أو vertex تاني. | <strong>SPARQL</strong> (مرتبطة بالـ Semantic Web و RDF). |
| <strong>Datalog</strong> | أقدم وأساس الحاجات دي (من الثمانينات). بتكتب <strong>rules</strong> وتبنيها فوق بعض زي الدوال. | بتستخدمه Datomic و Cascalog. أقل سهولة للحاجات البسيطة بس قوي جدًا للمعقد. |

<Box type="tip" title="قوة الجراف">

- أي vertex يقدر يتربط بأي vertex — مفيش schema يمنع.
- تمشي في الجراف للأمام والخلف بكفاءة (incoming/outgoing indexes).
- labels مختلفة تخليك تخزن أنواع معلومات كتير مع بعض وتفضل نضيفة.
- سهل يتطور: تضيف أنواع علاقات جديدة من غير ما تكسر القديم.
- الـ traversal بطول مش معروف مقدمًا (زي "اي حد ساكن في أي مكان جوه أوروبا") هو قوته الحقيقية.

</Box>

<Box type="warn" title="ماتلخبطش">

Graph DBs ≠ CODASYL: في CODASYL كان فيه schema بتحدد مين يتربط بمين، والوصول لازم يمشي في access path، والأطفال مترتبين. الجراف مفيهوش القيود دي وبيدعم لغات declarative.

</Box>

## 🧪 Lab

جرّب نفس الداتا في موديلين بـ PostgreSQL (فيه `jsonb` فبيعمل الاتنين):

```sql
-- relational
CREATE TABLE users (id serial PRIMARY KEY, name text);
CREATE TABLE positions (id serial PRIMARY KEY, user_id int REFERENCES users(id), title text, company text);

-- document: البروفايل كله في عمود واحد
CREATE TABLE profiles (id serial PRIMARY KEY, doc jsonb);
INSERT INTO profiles (doc) VALUES ('{"name":"Saeed","positions":[{"title":"FE Engineer","company":"X"}]}');

-- query جوه الـ JSON
SELECT doc->>'name' FROM profiles WHERE doc @> '{"positions":[{"company":"X"}]}';
```

بعدين جرّب `WITH RECURSIVE` على جدول `edges(from_id, to_id)` عشان تحس ليه الـ graph queries بتطول في SQL.
