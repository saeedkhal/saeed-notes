## الفكرة

كل record بيتبع <Hl c="y">partition واحد بالظبط</Hl>، وكل partition كأنه داتابيز صغيرة. الأسماء بتختلف: <En>shard</En> (MongoDB, Elasticsearch)، <En>region</En> (HBase)، <En>tablet</En> (Bigtable)، <En>vnode</En> (Cassandra, Riak)، <En>vBucket</En> (Couchbase). الهدف الأساسي: <strong>Scalability</strong> — توزيع الداتا والكويريز على ماكينات كتير.

وعادة بيتعمل مع الـ replication: كل partition له نسخ على كذا نود، وكل نود ممكن تبقى leader لبعض الـ partitions و follower لغيرها.

<Box type="story" title="تشبيه: دولاب الملفات" icon="🍽️">

لو عندك 10 موظفين وأرشيف ضخم، تقسم الملفات بينهم. لو قسمت غلط وموظف واحد مسك كل الشغل، باقي الموظفين قاعدين والمسكين غرقان = <strong>skew</strong>، والموظف ده اسمه <En>hot spot</En>.

</Box>

## تقسيم الـ Key-Value Data

أبسط طريقة: عشوائي — بيوزع كويس جدًا بس لما تدور على key مش هتعرف هو فين، فتسأل الكل. فيه طريقتين أحسن:

<Grid2>
<Card title="📚 By Key Range" c={1}>

زي مجلدات الموسوعة: A–B، C–D… كل partition مدى متصل من المفاتيح. (حدود المدى مش لازم متساوية — بتتظبط حسب الداتا.)<br/>✅ <strong>Range queries</strong> ممتازة (المفاتيح مترتبة جوه الـ partition).<br/>❌ <strong>Hot spots</strong>: لو المفتاح timestamp، كل كتابات النهارده تروح لـ partition واحد! الحل: حط حاجة قبل الوقت (اسم السينسور + الوقت).<br/>Bigtable, HBase, RethinkDB, MongoDB (قبل 2.4)

</Card>
<Card title="#️⃣ By Hash of Key" c={4}>

طبّق hash (مش لازم يكون قوي cryptographically، بس لازم ثابت — مش زي `hashCode()` في Java اللي ممكن يختلف بين processes)، وكل partition ياخد مدى من الـ hashes.<br/>✅ توزيع عادل.<br/>❌ <strong>ضاع الترتيب</strong> → range queries لازم تتبعت لكل الـ partitions.<br/>Cassandra, Riak, Voldemort, MongoDB (hash mode)

</Card>
</Grid2>

<Box type="idea" title="الحل الهجين في Cassandra">

<strong>Compound primary key</strong>: الجزء الأول بيتعمله hash ويحدد الـ partition، والباقي بيترتب جوه الـ partition (concatenated index). مثال: `(user_id, update_timestamp)` → تقدر تجيب كل بوستات يوزر معين في فترة زمنية بكويري range واحدة على partition واحد. وفيه برضه <En>consistent hashing</En> كمصطلح، بس الكتاب بيقول الأدق نسميه hash partitioning لأن الاسم ده بيتلخبط.

</Box>

### Skew و Hot Spots

حتى الـ hash مش بيحل كل حاجة: لو key واحد عليه حمل خرافي (سيليبريتي عنده ملايين متابعين بيعلقوا على بوسته)، كل الطلبات هتروح لنفس المكان. أغلب الداتابيزات مش بتحلها أوتوماتيك. الحل اليدوي: ضيف رقم عشوائي من 2 خانات لآخر المفتاح الساخن → يتوزع على 100 مفتاح. بس القراءة بقت لازم تجمع من الـ 100، ولازم تعرف أنهي مفاتيح محتاجة ده (book-keeping).

## Partitioning والـ Secondary Indexes

الـ primary key سهل. بس السؤال: "هات كل العربيات اللون الأحمر" — الـ index ده نقسمه إزاي؟

|   | 📄 Document-partitioned (Local index) | 🏷️ Term-partitioned (Global index) |
|---|---|---|
| الفكرة | كل partition عنده index لداتاه هو بس. | index واحد global بس مقسوم بقيمة الـ term نفسه (color:red في partition، color:silver في partition تاني). |
| الكتابة | ✅ سهلة — partition واحد. | ❌ أبطأ — كتابة document واحد ممكن تعدل كذا partition في الـ index. |
| القراءة | ❌ <strong>Scatter/gather</strong>: تسأل كل الـ partitions → tail latency amplification. | ✅ partition واحد بس للـ term. |
| ملاحظات | MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, VoltDB. | التحديث غالبًا <strong>async</strong> (DynamoDB: كسور ثانية عادة) فممكن تقرا index مش محدث. |

## Rebalancing — إعادة التوزيع

الحمل بيزيد، الداتا بتكبر، ماكينة بتموت… فلازم ننقل partitions بين النودز. المتطلبات: الحمل يفضل عادل، الداتابيز تفضل شغالة أثناء النقل، وماننقلش داتا أكتر من اللازم.

<Box type="warn" title="ليه hash mod N فكرة وحشة؟">

لو `hash(key) % N` و N اتغيرت من 10 لـ 11، <strong>تقريبًا كل المفاتيح هتتنقل</strong> لنود تانية! نقل داتا مالوش لازمة خالص.

</Box>

| الاستراتيجية | إزاي | ملاحظات |
|---|---|---|
| <strong>Fixed number of partitions</strong> | اعمل partitions أكتر بكتير من النودز (مثلًا 1000 لـ 10 نودز). نود جديدة "تسرق" partitions كاملة من الباقيين. الـ key → partition ثابت، اللي بيتغير بس partition → node. | Riak, Elasticsearch, Couchbase, Voldemort. لازم تختار العدد صح من الأول: كبير أوي = overhead، صغير أوي = partitions ضخمة صعب نقلها. |
| <strong>Dynamic partitioning</strong> | زي B-tree: partition كبر عن حد معين (HBase: 10GB) يتقسم نصين؛ صغر يتدمج مع جاره. | HBase, RethinkDB, MongoDB. عدد الـ partitions بيتكيف مع حجم الداتا. مشكلة: داتابيز فاضية = partition واحد → <strong>pre-splitting</strong>. ينفع للـ range والـ hash. |
| <strong>Proportional to nodes</strong> | عدد ثابت من الـ partitions لكل نود. نود جديدة تختار partitions عشوائي وتقسمهم وتاخد نصهم. | Cassandra (256 لكل نود افتراضيًا)، Ketama. محتاج hash partitioning. |

<Box type="tip" title="أوتوماتيك ولا يدوي؟">

الـ rebalancing عملية تقيلة (نقل داتا + شبكة). أوتوماتيك بالكامل ممكن يبقى خطير لو اتجمع مع اكتشاف أعطال أوتوماتيك: نود مضغوطة وبطيئة → السيستم يحسبها ماتت → يبدأ rebalancing → ضغط أكتر على الباقيين → <strong>cascading failure</strong>. عشان كده الأحسن إن السيستم يقترح وإنسان يوافق (Couchbase, Riak, Voldemort).

</Box>

## Request Routing — الطلب يروح فين؟

ده جزء من مشكلة أعم اسمها <En>service discovery</En>. تلات طرق:

<Grid2>
<Card title="1. أي نود" c={1}>

الكلاينت يكلم أي نود (round-robin). لو مش عندها الـ partition تحوّل الطلب. (Cassandra/Riak: gossip protocol بين النودز.)

</Card>
<Card title="2. Routing tier" c={4}>

طبقة في النص partition-aware load balancer بتوجه الطلب.

</Card>
<Card title="3. Client واعي" c={3}>

الكلاينت نفسه عارف الـ partition على أنهي نود.

</Card>
</Grid2>

السؤال الصعب: إزاي اللي بيوجّه يعرف التغييرات؟ ده consensus. أنظمة كتير بتستخدم <Hl c="g">ZooKeeper</Hl>: كل نود بتسجل نفسها، وZooKeeper يحتفظ بالـ mapping الموثوق، والـ routing tier يعمل subscribe على التغييرات. (HBase, SolrCloud, Kafka بتستخدمه؛ LinkedIn Espresso بيستخدم Helix فوقه؛ MongoDB عنده config servers و mongos.) وعمومًا الكلاينت بيعرف IPs الـ routing tier عن طريق DNS.

### Parallel Query Execution

الـ NoSQL غالبًا بيدعم كويريز بسيطة على key واحد. لكن داتابيزات <En>MPP</En> (Massively Parallel Processing) — المستخدمة في الـ analytics — بتقسم الكويري المعقدة (joins, filters, aggregations) لمراحل بتتنفذ بالتوازي على نودز وpartitions مختلفة.

## 🧪 Lab

جرّب الـ declarative partitioning في Postgres:

```sql
CREATE TABLE events (id bigserial, user_id int, created_at timestamptz)
  PARTITION BY HASH (user_id);
CREATE TABLE events_p0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE events_p1 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE events_p2 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE events_p3 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 3);

EXPLAIN SELECT * FROM events WHERE user_id = 7;      -- partition واحد
EXPLAIN SELECT * FROM events WHERE created_at > now() - interval '1 day';  -- كله
```

بعدين جرّبها `PARTITION BY RANGE (created_at)` وقارن.
