## الـ component يبقى رفيع

الـ component بيعمل حاجتين بس: **يعرض** و **ينقل نية المستخدم** للـ use case. مفيش قواعد بيزنس ولا `fetch`.

<File name="src/ui/jobs/usePublishJob.ts">

```ts
import { useMutation, useQueryClient } from "@tanstack/react-query";
import { useServices } from "../services";

export function usePublishJob() {
  const { publishJob } = useServices();
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: publishJob,
    onSuccess: (result, id) => {
      if (result.ok) queryClient.invalidateQueries({ queryKey: ["job", id] });
    },
  });
}
```

</File>

}

## الـ Composition Root: المكان الوحيد اللي يعرف كل حاجة

حد لازم يقول "الـ `JobRepository` في التطبيق الحقيقي هو `HttpJobRepository`". ده بيحصل في مكان **واحد** قريب من نقطة دخول التطبيق، اسمه **composition root**:

<File name="src/ui/services.tsx">

```tsx
import { createContext, useContext, type ReactNode } from "react";
import { makePublishJob } from "../application/publishJob";
import { HttpJobRepository } from "../infrastructure/httpJobRepository";

function createServices() {
  const jobs = new HttpJobRepository(import.meta.env.VITE_API_URL);
  const clock = { now: () => new Date() };
  return { publishJob: makePublishJob({ jobs, clock }) };
}

type Services = ReturnType<typeof createServices>;
const ServicesContext = createContext<Services | null>(null);

export function ServicesProvider({ children, services = createServices() }: { children: ReactNode; services?: Services }) {
  return <ServicesContext.Provider value={services}>{children}</ServicesContext.Provider>;
}

export function useServices() {
  const services = useContext(ServicesContext);
  if (!services) throw new Error("useServices must be used inside ServicesProvider");
  return services;
}
```

</File>

وفي Storybook أو تيست الـ component، بتمرّر `services` مبنية على `InMemoryJobRepository`، فالشاشة تشتغل من غير backend خالص.

<Box type="warn" title="createServices() كـ default parameter">

الـ default بيتحسب مع **كل render** للـ provider. ده مقبول لأن الـ provider بيترندر مرة في جذر التطبيق. لو هيترندر كتير، اعمل `createServices()` مرة واحدة بره الـ component ومرّرها.

</Box>

## شكل الفولدرات

<Tree>

```text
src/
├── domain/            ← مفيهوش import لأي حاجة بره domain
│   └── job.ts
├── application/       ← بيعمل import من domain بس
│   ├── ports.ts
│   └── publishJob.ts
├── infrastructure/    ← بينفّذ ports (domain + application)
│   ├── httpJobRepository.ts
│   └── inMemoryJobRepository.ts
└── ui/                ← React: components و hooks و services.tsx
    ├── services.tsx   ← الـ composition root
    └── jobs/
        ├── usePublishJob.ts
        └── PublishButton.tsx
```

</Tree>

<Box type="tip" title="خلّي الـ lint يحرس القاعدة">

القاعدة بتتكسر بالغلط في PR زحمة. استخدم `eslint-plugin-boundaries` أو قاعدة `no-restricted-imports` تمنع `domain/` إنه يعمل import من `ui/` أو `infrastructure/`. راجع الـ docs بتاعة الـ plugin لشكل الـ config.

</Box>

<Box type="interview" title="سؤال إنترفيو">

"تنظّم الفولدرات بالطبقات ولا بالـ feature؟" — في المشاريع الكبيرة الأحسن الاتنين: **feature أولًا** (`jobs/` و `candidates/`)، وجوه كل feature الطبقات (`domain` و `application` و `infrastructure` و `ui`). كده كل feature تقدر تتنقل أو تتقسم لوحدها.

</Box>
