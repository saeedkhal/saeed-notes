الـ <En>Clean Architecture</En> (فكرة Robert C. Martin، المعروف بـ Uncle Bob) بتقول: <Hl c="y">قواعد البيزنس متعتمدش على الـ framework ولا الـ API ولا الـ UI</Hl>. دول تفاصيل تنفيذ وممكن يتغيروا.

## الطبقات الأربعة

| الطبقة | فيها إيه | في الفرونت |
| --- | --- | --- |
| **Domain** (Entities) | الأنواع وقواعد البيزنس اللي نادرًا ما بتتغير | `type JobPosting` و `canPublish()` |
| **Application** (Use Cases) | سيناريوهات التطبيق: بتنسّق بين الـ domain والعالم الخارجي | `publishJob()` و `saveDraft()` |
| **Adapters** (Presentation + Infrastructure) | الترجمة بين جوه وبره | components و hooks، و repository بـ `fetch` |
| **Frameworks & Drivers** | الأدوات نفسها | React، axios، `localStorage`، المتصفح |

في أغلب مشاريع الفرونت بنجمع آخر طبقتين، فبيبقى عندك عمليًا **٣ دواير**: domain في القلب، وحواليها application، وبره خالص adapters (UI و infrastructure).

كل الأسهم رايحة **لجوه**. الطبقة اللي جوه **عمرها ما تعمل import** من طبقة بره. يعني:

- ملف في الـ domain مفيهوش `import React` ولا `fetch` ولا `axios`.
- الـ use case مش عارف إن في React أصلًا، ولا عارف الداتا جاية من REST ولا GraphQL.
- الـ component هو اللي يعرف الـ use case، مش العكس.

<Box type="story" icon="🏢" title="العمارة والبواب">

السكان (الـ domain) ميعرفوش البواب اسمه إيه ولا شيفته إمتى. البواب (الـ adapter) هو اللي يعرف أرقام الشقق وبيوصّل الطلبات. لو البواب اتغير، السكان مش هيحسوا. بس لو السكان اتنقلوا، البواب لازم يعرف.

</Box>

<Box type="warn" title="خلي بالك من اتجاه السهم">

اتجاه **الاعتمادية** (مين بيعمل import لمين) غير اتجاه **الداتا وقت التشغيل**. وقت التشغيل الطلب بيمشي من الـ UI لحد الـ API وراجع. بس في الكود، الـ use case مبيعملش import للـ API. هنشوف إزاي ده بيحصل في فصل ٣.

</Box>
